# EP13. 모니터링 & 트러블슈팅

> 시리즈: [폐쇄망 LLM 구축기](README.md) · 이전: [EP12. 오프라인 패키지 설치](EP12-오프라인-패키지-설치.md) · 다음: [EP14. 모델 업데이트 전략](EP14-모델-업데이트-전략.md)

EP02에서 4계층으로 나눈 이유, "장애 났을 때 원인을 빨리 찾기 위해서"라고 했었죠. 이번 편은 그 4계층에 실제로 어떤 지표를 걸었는지, 그리고 실제로 터졌던 장애 하나를 그대로 복기해볼게요.

## 📊 계층별로 다른 걸 본다

| 계층 | 주요 지표 | 어디서 나오나 |
|---|---|---|
| 서빙 계층 (vLLM) | GPU 사용률·온도, `vllm:gpu_cache_usage_perc`([[KV 캐시]] 점유율), `vllm:time_to_first_token_seconds` | vLLM `/metrics` (Prometheus) |
| 서빙 계층 (Ollama) | 임베딩 요청 지연시간 | Ollama 자체 로그 |
| 게이트웨이 계층 (LiteLLM) | 팀별 요청 수·실패율·[[처리량과 지연시간|토큰 처리량]] | LiteLLM `/metrics` |
| 접근 계층 (Open WebUI) | 동시 접속자 수, 세션 오류 | Open WebUI 로그 + nginx 액세스 로그 |

이걸 Prometheus가 전부 긁어가고, Grafana로 계층별 대시보드를 따로 만들었어요. "챗봇이 느려요"라는 민원이 오면 제일 먼저 `vllm:gpu_cache_usage_perc`부터 봅니다 — 이게 100%에 가깝다는 건 [[배치]]가 꽉 차서 새 요청이 대기하고 있다는 뜻이거든요.

```yaml
# prometheus.yml (일부)
scrape_configs:
  - job_name: vllm
    static_configs:
      - targets: ["vllm-server:8000"]
  - job_name: litellm
    static_configs:
      - targets: ["litellm-gateway:4000"]
```

## ⚠️ 실제로 터졌던 장애 — "오늘따라 챗봇이 느려요"

어느 날 오후 2시쯤 현업팀에서 "챗봇이 답을 잘 안 준다"는 문의가 몰렸어요. Grafana부터 열었더니 `vllm:gpu_cache_usage_perc`가 평소 40~50%대였는데 그날은 98%까지 찍혀 있더라구요. [[KV 캐시]]가 거의 꽉 찼다는 뜻이니, 누군가 엄청 긴 대화를 물고 있거나 아주 긴 프롬프트를 보내고 있다는 얘기였어요.

LiteLLM 로그에서 요청 크기 상위 목록을 뽑아보니, 현업팀 한 분이 **80페이지짜리 약관 PDF 전문을 통째로 복사해서 채팅창에 붙여넣고** "이거 요약해줘"라고 물어본 거였어요. [[컨텍스트 윈도우]] 안에는 들어갔지만, 이 요청 하나가 [[KV 캐시]]를 크게 잡아먹으면서 다른 사용자들 몫의 [[배치]] 여유가 사라진 거죠. 특정 요청 하나가 전체 [[처리량과 지연시간|처리량]]을 끌어내린, 딱 이론으로 배웠던 그 상황이 실제로 벌어진 거였어요.

**대응은 두 가지로 했어요.**

1. **즉시 조치**: LiteLLM 라우터에 요청당 최대 입력 토큰 상한(`max_input_tokens`)을 걸어서, 이런 식의 초대형 요청은 게이트웨이 단에서 먼저 걸러지게 했어요.
2. **재발 방지**: "긴 문서는 채팅창에 붙여넣지 말고, 문서 반입 절차를 거쳐 RAG로 미리 색인해두라"는 사용 가이드를 현업팀에 다시 안내했어요. 그게 바로 EP12에서 만든 경량 반입 파이프라인이 있는 이유였으니까요.

## 🔔 알람은 계층별로 다르게 걸었어요

- 서빙 계층: `gpu_cache_usage_perc > 90%`가 5분 이상 지속되면 인프라팀 슬랙 알람
- 게이트웨이 계층: 팀별 실패율(4xx/5xx)이 급증하면 알람
- 접근 계층: 로그인 실패가 짧은 시간에 몰리면 보안팀에도 알람 (이상 접근 시도 의심)

같은 "느려짐"이라도 원인이 계층마다 다르니까, 알람도 계층별로 다른 사람한테 가게 만든 게 핵심이었어요.
