# EP06. 반입 패키지 제작

> 시리즈: [폐쇄망 LLM 구축기](README.md) · 이전: [EP05. LiteLLM 설정](EP05-LiteLLM-설정.md) · 다음: [EP07. RHEL 9에서 Podman 컨테이너 운영](EP07-RHEL9-Podman-컨테이너-운영.md)

Phase 2 마지막 편이에요. EP04에서 모델·이미지를 받았고, EP05에서 설정 파일을 만들었으니, 이제 이걸 전부 모아서 실제로 반입 신청을 넣을 차례예요. "그냥 USB에 복사해서 들고 가면 되는 거 아니냐" 싶으실 텐데, 저희 회사는 반입물을 개별 파일 단위가 아니라 **패키지 단위**로 승인받게 되어 있어서, 이번 편에서는 그 패키지를 어떻게 구성했는지 적어볼게요.

## 📋 반입 패키지 폴더 구조

```
airgap-package-2026Q3/
├── manifest.json              # 전체 목록 + 메타데이터
├── CHECKSUMS.sha256           # EP04에서 뽑은 체크섬
├── models/
│   ├── qwen2.5-32b-gptq-int4/
│   └── bge-m3/
├── images/
│   ├── vllm-v100.tar
│   ├── ollama.tar
│   ├── litellm.tar
│   ├── qdrant.tar
│   └── open-webui.tar
└── configs/
    ├── litellm-config.yaml
    └── docker-compose.yml
```

`manifest.json`이 이번 편의 핵심이에요. 반입 심사하시는 분들이 파일을 하나하나 열어볼 시간이 없으니까, "뭐가 왜 들어왔는지"를 한 파일에 요약해뒀어요.

```json
{
  "package_id": "airgap-package-2026Q3",
  "requested_by": "IT인프라팀 (담당자명)",
  "purpose": "사내 문서 QA 챗봇 + 개발팀 코딩 어시스턴트 구축",
  "items": [
    {
      "path": "models/qwen2.5-32b-gptq-int4",
      "type": "model_weights",
      "source": "Qwen/Qwen2.5-32B-Instruct (원본), 사내 재양자화",
      "license": "Apache 2.0",
      "size_gb": 18.5,
      "contains_pii": false
    },
    {
      "path": "models/bge-m3",
      "type": "model_weights",
      "source": "BAAI/bge-m3 (Hugging Face)",
      "license": "MIT",
      "size_gb": 2.3,
      "contains_pii": false
    },
    {
      "path": "images/vllm-v100.tar",
      "type": "container_image",
      "source": "vllm-project/vllm 소스 빌드 (TORCH_CUDA_ARCH_LIST=7.0)",
      "license": "Apache 2.0",
      "size_gb": 12.1,
      "contains_pii": false
    }
  ],
  "checksum_file": "CHECKSUMS.sha256",
  "approval_status": "pending"
}
```

`contains_pii`(개인정보 포함 여부) 항목을 각 파일마다 명시한 게 포인트예요. EP04에서 캘리브레이션 데이터로 쓴 사내 문서 샘플도 개인정보보호 담당자 확인을 거쳐 `false`로 표시했고, 확인받은 근거(검토 이력)는 별도 문서로 첨부했습니다. 이 항목 하나 빠뜨리면 반입 심사가 통째로 반려돼서 처음부터 다시 신청해야 해요 — 저희도 첫 신청 때 이걸 빠뜨렸다가 한 번 반려당했습니다.

## ✅ 반입 전 셀프 체크리스트

`docs/01-roadmap.md` Part 8에 정리해둔 일반 절차를 저희 상황에 맞게 체크리스트로 다시 만들었어요.

- [ ] 확장자 화이트리스트 확인 — `.safetensors`, `.gguf`, `.tar`, `.yaml`, `.json`, `.sha256`, `.rpm`, `.whl`, `.vsix`만 포함, 그 외 실행 파일 없음
- [ ] 전 파일 백신 검사 완료 (대용량 모델 파일도 예외 없이)
- [ ] `manifest.json`의 `contains_pii` 항목 전수 확인 + 개인정보보호 담당자 서명
- [ ] `CHECKSUMS.sha256`이 실제 파일과 일치하는지 재확인 (`sha256sum -c`)
- [ ] LiteLLM 설정 파일에 마스터 키 등 민감값이 평문으로 없는지 확인
- [ ] 반입 신청서에 담당자·목적·예상 반입 주기(분기 1회) 명시

## 📌 반입 이후 검증까지 한 세트로

승인이 나서 패키지가 폐쇄망 안으로 넘어오면, 바로 운영 서버에 풀지 않고 격리된 테스트 구간에서 먼저 체크섬부터 재검증해요.

```bash
cd airgap-package-2026Q3
sha256sum -c CHECKSUMS.sha256
```

여기서 하나라도 불일치가 나오면 그 즉시 반입 프로세스를 중단하고 보안팀에 재확인을 요청하도록 내부 규정을 정해뒀어요. 다행히 아직까지 불일치가 난 적은 없었지만, 이 스텝을 생략하면 안 되는 이유는 명확해요 — 반입 구간을 거치는 동안 파일이 손상되거나 변조됐는지 확인할 수 있는 마지막 기회거든요.

Phase 2는 여기까지예요. 다음 Phase 3부터는 이 패키지를 실제로 폐쇄망 서버에 풀고, RHEL 9 위에서 Podman으로 컨테이너를 띄우는 얘기예요.
