# EP05. LiteLLM 설정

> 시리즈: [폐쇄망 LLM 구축기](README.md) · 이전: [EP04. 컨테이너 이미지 & 모델 다운로드](EP04-컨테이너-이미지-모델-다운로드.md) · 다음: [EP06. 반입 패키지 제작](EP06-반입-패키지-제작.md)

EP02에서 4계층 아키텍처 얘기할 때 "접근 계층 앞에 게이트웨이를 하나 세운다"고 했었죠. 이번 편은 그 게이트웨이, [[LiteLLM]] 설정 얘기예요. 아직 폐쇄망에 반입도 안 한 시점인데 설정부터 하냐고 물으실 수 있는데, 설정 파일 자체를 반입 대상에 포함시켜야 해서 인터넷망에서 미리 만들어두는 거예요.

## 🎯 왜 vLLM을 바로 안 열어주고 게이트웨이를 두냐면

처음엔 "그냥 Open WebUI가 vLLM을 바로 보게 하면 되지 않나" 싶었는데, 팀 두 개(현업 40명, 개발팀 25명)가 같이 쓰는 순간부터 얘기가 달라져요.

- 현업팀이 던지는 요청 때문에 개발팀 코드 자동완성이 밀리면 안 돼요 — 팀별 요청량 제한이 필요해요.
- 누가 언제 뭘 물어봤는지 감사 로그가 있어야 해요 (EP11에서 더 다룰 거예요).
- 나중에 모델을 Qwen에서 다른 모델로 바꿀 때, 클라이언트(Open WebUI, Continue.dev) 설정은 안 건드리고 게이트웨이 쪽만 바꾸고 싶었어요.

이 세 가지가 전부 "vLLM 앞단에 뭔가 하나 더 있어야 한다"는 결론으로 이어졌고, [[표준 아키텍처]]에서 얘기했던 API 게이트웨이 자리를 LiteLLM으로 채웠습니다.

## 📋 설정 파일은 이렇게 짰어요

```yaml
# litellm-config.yaml
model_list:
  - model_name: qwen2.5-32b
    litellm_params:
      model: openai/qwen2.5-32b-gptq-int4
      api_base: http://vllm-server:8000/v1
      api_key: "dummy-key"

  - model_name: bge-m3-embed
    litellm_params:
      model: openai/bge-m3
      api_base: http://ollama-server:11434/v1
      api_key: "dummy-key"

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
  database_url: os.environ/LITELLM_DB_URL

router_settings:
  routing_strategy: least-busy
  num_retries: 2
  timeout: 30
```

`api_base`가 전부 폐쇄망 내부 호스트명(`vllm-server`, `ollama-server`)을 가리키고 있고, 외부 URL은 하나도 없어요. LiteLLM 자체도 기본적으로 사용량 리포팅 같은 걸 어딘가로 보내려는 옵션이 있는 서비스라, 이런 자체 텔레메트리 옵션도 다 꺼서 설정에 명시했습니다. 폐쇄망 안의 어떤 구성요소도 스스로 인터넷에 나가면 안 된다는 원칙, EP02에서부터 계속 반복되는 얘기예요.

`master_key`나 `database_url`처럼 민감한 값은 설정 파일에 그대로 박지 않고 환경변수(`os.environ/...`)로 빼뒀어요. 이 파일 자체가 반입 심사를 거치는데, 심사하는 분들이 파일을 열어봤을 때 키 값이 그대로 노출돼 있으면 곤란하니까요.

### 설정값 하나하나가 뭔지 (처음 보면 헷갈리는 부분)

**`model_list` — 별칭과 실제 주소를 연결**

| 값 | 뭔지 | 왜 필요한가 |
|---|---|---|
| `model_name: qwen2.5-32b` | 클라이언트가 부르는 **별칭(가짜 이름)** | 실제 서버 주소를 클라이언트가 몰라도 되게 함. EP14에서 이 이름만 그대로 두고 뒷단 모델을 바꿨던 게 이 필드 덕분 |
| `model: openai/qwen2.5-32b-gptq-int4` | `제공자스타일/실제모델명` 형식 | "openai" 부분은 이 백엔드한테 **OpenAI 호환 방식으로 말 걸라**는 뜻 — LiteLLM이 여러 제공자(OpenAI, Anthropic, Ollama 등)를 지원하니 어떤 언어로 대화할지 지정하는 것 |
| `api_base` | 실제 서버 주소(`vllm-server:8000` 등) | 별칭 뒤에 진짜로 숨어있는 물리적 위치. 클라이언트는 이 주소를 몰라도 됨 |
| `api_key: "dummy-key"` | 그냥 채워 넣은 값 | vLLM 자체는 폐쇄망 내부용이라 키 검사를 안 하는데, LiteLLM 클라이언트 라이브러리가 이 필드를 비워두는 걸 허용 안 해서 형식만 맞추려고 넣은 더미값 |

**`general_settings` — 게이트웨이 자체의 관리 설정**

| 값                    | 뭔지                            | 왜 필요한가                                 |
| -------------------- | ----------------------------- | -------------------------------------- |
| `master_key`         | LiteLLM의 관리자 비밀번호             | 이 키를 가진 사람만 가상 키를 새로 발급하거나 설정을 바꿀 수 있음 |
| `database_url`       | Postgres 접속 주소(EP10)          | 가상 키·예산·사용 이력을 여기 저장해야 재부팅해도 안 사라짐     |
| `os.environ/...` 접두사 | "파일에 직접 안 쓰고 환경변수에서 읽어와라"라는 뜻 | 반입 심사자가 파일을 열어봐도 실제 키 값이 노출되지 않게 하려고   |

**`router_settings` — 요청을 어떻게 처리할지**

| 값 | 뭔지 | 왜 필요한가 |
|---|---|---|
| `routing_strategy: least-busy` | 백엔드가 여러 대일 때 "지금 제일 한가한 곳"으로 보냄 | 서버 1대뿐인 지금은 의미 없지만, GPU를 증설해 서버가 여러 대 되면 요청을 나눌 기준이 됨 (세션 고정은 아님 — 대화 하나가 요청마다 다른 서버로 갈 수 있어 [[KV 캐시]] 관점에선 아직 한계가 있는 방식) |
| `num_retries: 2` | 요청 실패 시 최대 2번 더 재시도 | GPU 순간 지연·네트워크 끊김 같은 일시적 오류로 사용자 요청이 바로 실패하지 않게 완충 |
| `timeout: 30` | 30초 안에 응답 없으면 실패 처리 | EP02 목표(전체 응답 20초 이내)에 여유를 좀 두고, 응답이 무한정 안 오는 걸 방지 |

## 팀별 가상 키(virtual key) 발급

LiteLLM이 뜬 다음에 실제로 발급하는 건 폐쇄망 안에서 하는 작업이지만, 어떤 값으로 발급할지는 미리 정해뒀어요.

```bash
curl -X POST http://litellm-gateway:4000/key/generate \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" \
  -d '{
    "models": ["qwen2.5-32b", "bge-m3-embed"],
    "team_id": "product-planning",
    "max_budget": 50,
    "budget_duration": "30d"
  }'
```

현업팀(`product-planning`)이랑 개발팀(`dev-team`)을 서로 다른 `team_id`로 나누고, 각자 예산(요청량 상한)을 따로 걸었어요. 이렇게 해두면 한 팀이 갑자기 요청을 몰아 보내도 다른 팀 서비스 품질에는 영향이 안 가요 — EP02에서 "챗봇이 느려요"라는 민원의 원인을 계층별로 가려낸다고 했었는데, 이 팀별 예산 분리도 같은 맥락이에요.

| 값 | 뭔지 | 왜 필요한가 |
|---|---|---|
| `models: [...]` | 이 키로 부를 수 있는 모델 목록 | 팀마다 접근 가능한 모델을 제한(개발팀 전용 모델은 현업팀 키로 못 부르게) |
| `team_id` | 이 키가 어느 팀 소속인지 태그 | 사용량·예산이 팀별로 집계되는 기준 |
| `max_budget: 50` | 이 키의 사용 한도 | 한 팀이 무제한으로 쓰는 걸 막음 |
| `budget_duration: "30d"` | 한도가 30일마다 초기화 | 일회성이 아니라 매달 반복되는 한도로 만듦 |

**여기서 헷갈리기 쉬운 부분**: 이 키는 팀당 딱 1개씩이지, 새 직원이 들어올 때마다 발급하는 게 아니에요. 새 직원은 그냥 사내 AD 계정으로 Open WebUI([[Continue.dev|또는 Continue.dev]])에 로그인하면 되고, 그 팀이 이미 갖고 있는 키를 그대로 씁니다. 누가 개인적으로 뭘 물었는지는 LiteLLM이 아니라 EP11의 LDAP 로그인·Open WebUI 로그에서 구분해요. 이 키는 완전히 새로운 팀(부서)이 통째로 시스템에 합류할 때만 새로 발급합니다.
