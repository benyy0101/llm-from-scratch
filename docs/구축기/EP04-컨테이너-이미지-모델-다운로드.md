# EP04. 컨테이너 이미지 & 모델 다운로드

> 시리즈: [폐쇄망 LLM 구축기](README.md) · 이전: [EP03. GPU 선택 가이드](EP03-GPU-선택-가이드.md) · 다음: [EP05. LiteLLM 설정](EP05-LiteLLM-설정.md)

이제부터는 Phase 2, "인터넷망 준비 편"이에요. 폐쇄망 안에는 아무것도 없으니까, 인터넷 되는 스테이징 서버에서 필요한 걸 전부 미리 받아놓고 검증까지 마친 다음에 반입해야 해요. 이번 편은 그중에서도 가장 부피가 큰 두 가지 — 모델 가중치랑 컨테이너 이미지 — 를 준비하는 이야기입니다.

## 📋 뭘 받아야 하는지부터 목록으로 뽑았어요

| 구분             | 내용                            | 예상 용량   |
| -------------- | ----------------------------- | ------- |
| LLM 가중치        | Qwen2.5-32B-Instruct 원본(FP16) | 약 64GB  |
| 임베딩 모델         | BGE-M3                        | 약 2.3GB |
| vLLM 이미지       | V100(sm_70) 지원을 켜서 직접 빌드      | 약 12GB  |
| Ollama 이미지     | 임베딩 서빙용                       | 약 1GB   |
| LiteLLM 이미지    | 게이트웨이                         | 약 1.5GB |
| Qdrant 이미지     | 벡터DB                          | 약 300MB |
| Open WebUI 이미지 | 현업용 채팅 UI                     | 약 2GB   |

목록을 미리 표로 뽑아둔 이유가 있어요. 반입 신청서에 "뭘, 왜, 얼마나" 들여오는지 적어야 하는데, 이걸 나중에 하나씩 기억해서 채우려면 꼭 뭔가 빠뜨리거든요.

이 표에 나온 게 다 뭔지 모르겠다면 vault 노트를 하나씩 보시면 됩니다 — [[Qwen]](LLM), [[BGE-M3]](임베딩 모델), [[vLLM]], [[Ollama]], [[LiteLLM]], [[Qdrant]](벡터DB), [[Open WebUI]] 순서대로 표와 매칭됩니다.

## 🖥️ LLM 가중치부터 받았어요

```bash
pip install "huggingface_hub[cli]"
huggingface-cli download Qwen/Qwen2.5-32B-Instruct \
  --local-dir ./staging/models/qwen2.5-32b-instruct
```

EP03에서 얘기했듯 V100(Volta)에서는 [[AWQ]]가 안 돌아서, 이 원본을 GPTQ Int4로 재양자화해야 해요. 커뮤니티에 이미 올라온 GPTQ 체크포인트가 있으면 그걸 우선 쓰고, 우리 도메인(금융 상품 매뉴얼, 사내 규정)에 맞게 다시 양자화하고 싶으면 직접 돌립니다.

```bash
pip install auto-gptq optimum accelerate
python quantize_gptq.py \
  --model Qwen/Qwen2.5-32B-Instruct \
  --bits 4 \
  --calib-data ./calib/internal_docs_sample.jsonl \
  --output ./staging/models/qwen2.5-32b-gptq-int4
```

`--calib-data`에 넣은 `internal_docs_sample.jsonl`이 포인트예요. [[GPTQ]]는 캘리브레이션 데이터를 흘려보면서 오차를 보상하는 방식이라, 영어 위키피디아 텍스트로 캘리브레이션하면 정작 우리가 쓸 한국어 금융 문서에서는 양자화 손실이 더 크게 날 수 있어요. 그래서 사내 상품 매뉴얼 중 개인정보 없는 샘플만 추려서 캘리브레이션 데이터로 썼습니다. (개인정보 포함 여부는 이 작업을 시작하기 전에 개인정보보호 담당자한테 먼저 확인받았어요 — 나중에 문제 되면 정말 골치아파지거든요.)

## 🐳 vLLM 이미지는 직접 구워야 했어요

순정 vLLM pip 패키지는 V100(sm_70)을 기본으로 안 켜놔서, 소스에서 직접 빌드했어요.

```bash
git clone https://github.com/vllm-project/vllm.git
cd vllm
docker build -f Dockerfile \
  --build-arg TORCH_CUDA_ARCH_LIST="7.0" \
  -t vllm-v100:latest .
```

이거 빌드하는 데 40분 넘게 걸려서 커피 두 잔 마셨어요. CUDA 버전이랑 드라이버 버전 맞추는 것도 은근히 까다로웠는데, 저희 서버에 깔린 드라이버 버전 기준으로 `TORCH_CUDA_ARCH_LIST`를 정확히 맞춰야 빌드가 통과하더라구요. 이 부분은 EP08(vLLM 배포)에서 더 자세히 다룰게요.

나머지 이미지(Ollama, LiteLLM, Qdrant, Open WebUI)는 순정 이미지 그대로 받아서 저장했습니다.

```bash
docker pull ollama/ollama:latest
docker pull ghcr.io/berriai/litellm:main-stable
docker pull qdrant/qdrant:latest
docker pull ghcr.io/open-webui/open-webui:main

docker save vllm-v100:latest -o ./staging/images/vllm-v100.tar
docker save ollama/ollama:latest -o ./staging/images/ollama.tar
docker save ghcr.io/berriai/litellm:main-stable -o ./staging/images/litellm.tar
docker save qdrant/qdrant:latest -o ./staging/images/qdrant.tar
docker save ghcr.io/open-webui/open-webui:main -o ./staging/images/open-webui.tar
```

## ✅ 체크섬까지 미리 뽑아뒀어요

반입 심사에서 "원본이랑 다른 파일 아니냐"는 질문이 꼭 나와요. 그래서 전송 전에 체크섬을 미리 뽑아 별도 파일로 남겨뒀습니다.

```bash
find ./staging -type f \( -name "*.safetensors" -o -name "*.tar" -o -name "*.jsonl" \) \
  -exec sha256sum {} \; > ./staging/CHECKSUMS.sha256
```

이 체크섬 파일 자체도 반입 대상에 포함시켰어요 — 폐쇄망에 들어간 뒤에 이 파일 기준으로 다시 검증하려면 파일 자체도 같이 들어가 있어야 하니까요.
