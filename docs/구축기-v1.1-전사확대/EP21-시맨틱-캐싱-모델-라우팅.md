# EP21. 시맨틱 캐싱 + 모델 라우팅

> v1.1: [전사 확대](README.md) · 이전: [EP20. AI 게이트웨이 보안 강화](EP20-AI-게이트웨이-보안-강화.md) · 다음: [EP22. 부하 테스트 방법론 + 카오스 엔지니어링](EP22-부하테스트-카오스엔지니어링.md)

컴플라이언스 심의는 통과했으니, 이번엔 순수 용량 문제예요. 전사 확대 대상이 300명 가까이로 늘어나는데, GPU 증설 예산은 다음 분기 품의 대상이에요. **지금 있는 V100 3장으로 이 트래픽을 버텨야** 했습니다. EP13 모니터링 데이터를 다시 들여다보니 실마리가 두 개 보였어요 — 사내 규정 QA에 "연차 며칠이야?" 류의 반복 질문이 상당히 많다는 것, 그리고 그런 질문들은 32B급 모델이 아니어도 충분히 답할 수 있는 난이도라는 것.

## 🗄️ 시맨틱 캐싱 — 반복 질문은 아예 모델까지 안 감

EP15에서 이미 [[Qdrant]]를 [[RAG]] 저장소로 쓰고 있었으니, 새 인프라를 안 늘리고 **컬렉션만 하나 더 만들어서** 캐시 저장소로 재활용했어요.

```yaml
model_list:
  - model_name: bge-m3-embed          # EP09에서 이미 있던 임베딩 모델
    litellm_params:
      model: openai/bge-m3
      api_base: http://ollama-server:11434/v1

litellm_settings:
  cache: True
  cache_params:
    type: qdrant-semantic
    qdrant_semantic_cache_embedding_model: bge-m3-embed
    qdrant_collection_name: "docsqa_semantic_cache"   # internal_docs와 별도 컬렉션
    qdrant_semantic_cache_vector_size: 1024            # BGE-M3 임베딩 차원, EP15와 동일
    similarity_threshold: 0.8
    semantic_cache_scope: end_user
```

"연차는 며칠이야?"랑 "연차 일수 알려줘"처럼 표현만 다르고 의미가 같은 질문이 오면, 코사인 유사도 0.8 이상일 때 모델 호출 없이 예전 답변을 그대로 돌려줘요. 정확히 같은 문장일 때만 맞히는 캐시가 아니라 **의미가 비슷하면 맞히는 캐시**라는 게 핵심입니다.

## ⚠️ 삽질 6 — Continue.dev(코딩 어시스턴트)엔 이 캐시를 켜면 안 돼요

처음엔 게이트웨이 전체에 일괄 적용했다가, 개발팀에서 "분명 코드를 고쳤는데 자동완성이 예전 코드 기준으로 제안한다"는 얘기가 나왔어요. LiteLLM 공식 문서에도 이 케이스가 경고로 적혀 있더라구요 — 시맨틱 캐싱은 멀티턴 대화나 에이전트형 워크플로처럼 **맥락이 계속 바뀌는 대화**에서는 "의미가 비슷한 예전 답변"을 잘못 재사용해 낡은 응답을 내놓을 수 있다는 거예요. 코딩 어시스턴트가 딱 이 케이스였죠.

그래서 캐시는 `dev-team` 가상 키(EP10)가 쓰는 모델엔 끄고, `product-planning` 가상 키의 단발성 문서QA 트래픽에만 켜는 걸로 정리했어요. LiteLLM에서 팀별로 이미 나눠뒀던 가상 키 구조(EP10)가 여기서도 그대로 써먹혔습니다.

## 🚦 모델 라우팅 — GPU 배치를 다시 짬

캐싱만으로는 "처음 묻는 질문"의 부하까지 줄일 수 없으니, 모델 자체를 두 단으로 나누기로 했어요. EP08에서 V100 3장 전부를 32B 모델 하나(`--tensor-parallel-size 3`)에 몰아줬던 걸, 이번엔 이렇게 재배치했습니다.

| GPU | 이전 (EP08) | 이후 |
|---|---|---|
| GPU 0, 1 | Qwen2.5-32B (TP=3, 3장 공유) | Qwen2.5-32B (TP=2) |
| GPU 2 | 〃 | Qwen2.5-7B (단일 GPU, TP 없음) |

재밌는 부작용도 하나 있었어요. Qwen2.5-32B는 attention head가 40개인데, 이걸 3장에 나누면 13.33개라 딱 안 떨어져서 내부적으로 불균형하게 샤딩돼 있었더라구요(EP08 때는 몰랐던 부분이에요). 2장으로 바꾸니 20개씩 정확히 나뉘어서, 오히려 이 불균형이 자연스럽게 해소됐습니다. 물론 GPU 한 장을 덜 쓰는 만큼 32B 모델 자체의 최대 처리량은 줄어드는 트레이드오프가 있는데, 그 손실을 라우팅으로 상쇄할 수 있는지가 이번 편의 핵심이었어요.

```bash
podman run -d --name vllm-32b \
  --device nvidia.com/gpu="0,1" --network airgap-net \
  -v /opt/models/qwen2.5-32b-gptq-int4:/models/qwen2.5-32b:Z -p 8000:8000 \
  localhost/vllm-v100:latest \
  vllm serve /models/qwen2.5-32b --tensor-parallel-size 2 --quantization gptq

podman run -d --name vllm-7b \
  --device nvidia.com/gpu="2" --network airgap-net \
  -v /opt/models/qwen2.5-7b-gptq-int4:/models/qwen2.5-7b:Z -p 8002:8000 \
  localhost/vllm-v100:latest \
  vllm serve /models/qwen2.5-7b --quantization gptq
```

Qwen2.5-7B는 EP04~06 방식 그대로 인터넷망에서 미리 받아 GPTQ Int4로 재양자화해 반입했어요 — 새로운 반입 절차가 아니라 기존 절차의 반복이라 이 부분은 크게 삽질할 게 없었습니다.

## 🧭 LiteLLM auto_router로 클라이언트를 안 건드리고 연결

EP14에서 썼던 "클라이언트는 모델 별칭만 알고 있고, 실제 뒷단은 LiteLLM 설정에서만 바뀐다"는 트릭을 여기서도 그대로 씁니다. Open WebUI·Continue.dev는 여전히 `qwen2.5-32b`라는 이름 하나만 호출하고, 그 이름 뒤에서 두 모델 중 뭘 쓸지는 LiteLLM이 결정해요.

```yaml
model_list:
  - model_name: qwen2.5-7b-backend
    litellm_params: { model: openai/qwen2.5-7b, api_base: http://vllm-7b:8000/v1 }
  - model_name: qwen2.5-32b-backend
    litellm_params: { model: openai/qwen2.5-32b, api_base: http://vllm-32b:8000/v1 }

  - model_name: qwen2.5-32b     # 클라이언트가 실제로 호출하는 이름 (EP14와 동일한 별칭 트릭)
    litellm_params:
      model: auto_router/complexity_router
      complexity_router_config:
        tiers:
          SIMPLE: qwen2.5-7b-backend
          MEDIUM: qwen2.5-32b-backend
          COMPLEX: qwen2.5-32b-backend
          REASONING: qwen2.5-32b-backend
        classifier_type: heuristic   # 정규식·키워드 기반, 1ms 미만, 외부 호출 없음
      complexity_router_default_model: qwen2.5-32b-backend
```

`classifier_type`을 `llm`(LLM한테 직접 물어봐서 난이도 판별)이 아니라 `heuristic`으로 잡은 게 의도적인 선택이었어요. `llm` 방식이 더 정교하게 분류하긴 하지만, 판별 자체에 모델 호출이 한 번 더 필요해서 지연시간이 늘어나요. EP20에서 프롬프트 인젝션 판별에 `llm_api_check`를 쓰면서 이미 지연시간 예산을 좀 썼는데, 여기까지 `llm` 분류를 얹으면 EP02에서 잡은 "첫 토큰 3초" 목표가 위태로워질 것 같아서 가장 가벼운 방식으로 잡았습니다.

## ✅ 2주 관찰 결과

| 지표 | 이전 | 이후 |
|---|---|---|
| 캐시 히트율 (문서QA만) | - | 약 22% |
| 7B로 라우팅된 비율 | - | 약 35% |
| 32B GPU 평균 사용률 | 60~70% | 40~50% |
| 동시 처리 가능 추정 인원 | 15명 | 40명대 |

캐시와 라우팅을 합치니 32B 모델이 처리해야 할 실제 요청량이 크게 줄었고, GPU 한 장 손해를 보고도 전체적으로는 여유가 생겼어요. 다만 이 수치는 실험실 관찰치라, 실제 300명 규모로 검증하는 건 다음 편의 몫입니다.
