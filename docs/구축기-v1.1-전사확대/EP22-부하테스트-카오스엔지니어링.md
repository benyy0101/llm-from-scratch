# EP22. 부하 테스트 방법론 + 카오스 엔지니어링

> v1.1: [전사 확대](README.md) · 이전: [EP21. 시맨틱 캐싱 + 모델 라우팅](EP21-시맨틱-캐싱-모델-라우팅.md)

v1.1 마지막 편이에요. EP19~21에서 컴플라이언스·보안·용량을 다 손봤으니, 이제 전사 확대 오픈 전에 **진짜 규모로 검증**할 차례예요. EP08에서 했던 벤치마크는 사실 "동시 15개 요청을 스크립트로 던져본" 수준이었는데, 이번엔 제대로 된 방법론으로 다시 재봤습니다.

## 📏 EP08 테스트의 한계 — "완료됐다"만 보고 있었어요

EP08에서 잰 건 평균 첫 토큰 지연·평균 전체 응답 시간이었어요. 근데 평균은 함정이 있죠 — 요청 100개 중 90개가 1초, 10개가 15초 걸려도 평균은 괜찮아 보여요. 실제로 사용자가 체감하는 "이 시스템 느리다"는 인식은 꼬리(tail) 쪽, 즉 p99에서 결정된다는 걸 EP13 장애(80페이지 붙여넣기 사고) 때 이미 배웠었는데, 정작 벤치마크 방법론엔 그걸 안 반영하고 있었더라구요.

## 🛠️ vLLM 공식 벤치마크 도구로 교체

자체 스크립트 대신 vLLM이 공식 제공하는 `vllm bench serve`를 썼어요. OpenAI 호환 엔드포인트를 그대로 때릴 수 있고, TTFT(첫 토큰까지)·ITL(토큰 간 간격)·E2EL(전체 응답)을 p50/p99까지 다 뽑아줘요.

```bash
vllm bench serve \
  --model qwen2.5-32b \
  --host litellm-gateway --port 4000 \
  --num-prompts 200 \
  --request-rate 20 \
  --percentiles 50,90,99 \
  --goodput ttft:3000 e2el:20000
```

`--goodput ttft:3000 e2el:20000`이 이번 벤치마크의 핵심이었어요. EP02에서 잡았던 목표(첫 토큰 3초, 전체 20초)를 **그대로 SLO 기준값으로 넣어서**, "완료된 요청 수"가 아니라 "이 두 기준을 동시에 만족한 요청의 비율(goodput)"을 직접 뽑아낼 수 있었거든요. EP02에서 숫자로 잡아둔 목표가 4개 편이 지난 지금도 그대로 벤치마크 기준으로 쓰이고 있다는 게, 그때 숫자부터 잡아둔 보람이 있었던 부분이에요.

## 📈 동시 사용자 램프업

EP02 목표(15명)에서 시작해서 전사 확대 목표(300명 예상, 피크 시 동시 접속은 그보다 훨씬 적을 것으로 추정)까지 단계적으로 올렸어요.

| 동시 접속 | Goodput (TTFT 3초 & E2E 20초 동시 충족) |
|---|---|
| 15명 (기존 목표) | 99% |
| 40명 (EP21 목표) | 96% |
| 100명 | 81% |

100명 구간에서 goodput이 눈에 띄게 떨어지는 지점을 확인했고, 이걸 "전사 확대 1차는 300명 대상이지만 동시 접속 100명을 넘기면 사용자 안내 문구(피크 시간대 분산 이용 요청)를 노출한다"는 운영 기준으로 정리했어요. GPU를 더 늘리지 않고 이 숫자 자체를 올리는 건 다음 분기 A100 증설 논의로 넘겼습니다.

## 💥 카오스 엔지니어링 — GPU 3장 중 1장이 죽으면?

부하가 아니라 **장애 자체**를 일부러 일으켜보는 것도 이번에 처음 했어요. Kubernetes 기반 도구(Chaos Mesh, LitmusChaos)는 우리 환경(RHEL 9 + Podman, 오케스트레이션 없음)엔 안 맞아서, Podman을 직접 지원하는 [[카오스 엔지니어링|Pumba]]를 썼습니다.

```bash
# 32B 컨테이너를 요청 처리 도중 강제 종료
sudo pumba --runtime podman kill vllm-32b

# LiteLLM-Qdrant 사이 네트워크에 지연 주입
sudo pumba --runtime podman netem --duration 3m delay --time 2000 qdrant
```

### ⚠️ 삽질 7 — rootless 컨테이너엔 일부 카오스 주입이 안 먹혀요

`kill`은 rootless든 rootful이든 잘 됐는데, `netem`·`stress`처럼 네트워크·리소스에 개입하는 명령은 rootless Podman에서 조용히 실패했어요. Pumba가 이런 개입을 하려면 컨테이너 네트워크 네임스페이스에 더 깊이 들어가야 하는데, 그 권한이 rootless엔 없더라구요. EP08에서 vLLM 컨테이너 하나만 rootful 예외를 뒀던 것처럼, 이번에도 **게임데이 진행 시간에만** LiteLLM·Qdrant 컨테이너를 임시로 rootful로 올렸다가, 테스트가 끝나면 바로 rootless로 되돌리는 방식으로 정리했어요. "예외는 항상 시간·범위를 좁혀서, 끝나면 되돌린다"는 원칙을 여기서도 지켰습니다.

### 결과 — GPU 재배치(EP21)가 뜻밖에 복원력도 올려줬어요

`vllm-32b`(GPU 0,1)를 강제 종료했을 때, EP08 구성(32B가 TP=3로 3장을 다 씀)이었다면 전체 서비스가 완전히 멈췄을 상황이에요. 근데 EP21에서 7B를 GPU 2에 독립적으로 분리해둔 덕분에, **복잡한 질문은 실패해도 간단한 질문(complexity_router가 SIMPLE로 분류하는 것들)은 계속 응답**이 됐어요. 용량 문제를 풀려고 한 결정이 부수적으로 부분 장애 허용성까지 만들어준 셈이었습니다.

## 🩺 GPU 하드웨어 장애는 어떻게 대비하나

Pumba로 컨테이너를 죽이는 건 소프트웨어 계층 장애고, 실제 GPU 하드웨어 장애는 다르게 나타나요. NVIDIA DCGM의 오류 주입 기능(`dcgmi test --inject`)도 살펴봤는데, 이건 **모니터링·알람 파이프라인이 제대로 반응하는지**를 테스트하는 도구지, 실제 하드웨어에 장애를 일으키는 게 아니었어요(`nvidia-smi -q -d ECC`엔 반영도 안 됨). 그래서 이번엔 여기까지만 확인하고, 실제 하드웨어 장애 시 리눅스 커널이 `dmesg`에 남기는 XID 에러 코드를 운영팀 참고용으로 정리해두는 선에서 마무리했어요.

| XID | 의미 | 대응 |
|---|---|---|
| 79 | GPU가 버스에서 이탈 (falling off the bus) | 서버 재부팅 필요 |
| 119 / 145 | GSP RPC 타임아웃 / NVLink 오류 | GPU 리셋 필요 |

## 🗓️ 게임데이 정례화

이번 한 번으로 끝내지 않고, EP14의 모델 갱신 주기(분기 1회)에 맞춰 **분기 1회 게임데이**를 정례화하기로 했어요. 모델을 교체하는 시점에 인프라 복원력도 같이 재검증하면, 두 일정을 따로 잡을 필요가 없으니까요.
