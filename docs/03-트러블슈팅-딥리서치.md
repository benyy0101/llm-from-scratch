## 1. RHEL 9 + Podman rootless GPU

EP07·EP08에서는 "rootless Podman + CDI로 GPU를 물리려다 간헐적 인식 실패 → vLLM만 rootful 예외"까지 다뤘습니다. 실제로는 이 조합에서 그보다 훨씬 다양한 각도의 문제가 보고돼 있습니다.

### CDI 스펙이 드라이버 업데이트 후 stale 참조로 남아 GPU 인식 실패
- **문제 상황**: `podman run --device nvidia.com/gpu=all` 실행 시 `Error: setting up CDI devices: failed to inject devices: failed to stat CDI host device "/dev/dri/renderD129": no such file or directory`.
- **원인**: `/etc/cdi/nvidia.yaml`이 생성 당시의 GPU 장치 경로를 그대로 참조하는데, 드라이버 업데이트나 GPU 구성 변경 후 CDI 스펙을 재생성하지 않아 stale 참조로 남음.
- **해결/우회**: `sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml`로 재생성. GPU 추가/제거·MIG 구성 변경·드라이버 업그레이드 후에는 CDI 스펙 재생성을 운영 체크리스트에 고정 항목으로 넣을 것.
- **출처**: [NVIDIA/nvidia-container-toolkit#885](https://github.com/NVIDIA/nvidia-container-toolkit/issues/885) — GitHub 이슈, 2025-01-30

### Rootless 모드에서는 cgroup 기반 GPU 격리 자체가 무력화됨
- **문제 상황**: 특정 태스크에 GPU 2장만 할당했는데, 동일 노드의 rootless Podman 컨테이너 안에서는 노드의 GPU 전체(8장)가 다 보임.
- **원인**: rootless 모드는 사용자 네임스페이스 권한 제약으로 NVIDIA Container Toolkit이 devices cgroup을 조작할 권한이 없어, cgroup 기반 GPU 접근 제한이 아예 작동하지 않음.
- **해결/우회**: 공식적으로 해결되지 않은 구조적 한계. CDI로 `--device nvidia.com/gpu=<index>`처럼 필요한 GPU만 명시적으로 지정하는 것이 실질적 완화책.
- **출처**: [NVIDIA/nvidia-container-toolkit#585](https://github.com/NVIDIA/nvidia-container-toolkit/issues/585) — GitHub 이슈, 2024-07-08

### rootless 모드는 cgroup v2 자체를 지원하지 않아 NVIDIA 훅이 실패
- **문제 상황**: NVIDIA Container Toolkit이 rootless 모드에서 GPU 컨테이너 실행 자체에 실패.
- **원인**: rootless 컨테이너는 devices cgroup을 직접 다룰 권한이 없어 NVIDIA OCI 훅이 cgroup 설정 시도 중 실패.
- **해결/우회**: `/etc/nvidia-container-runtime/config.toml`에서 `no-cgroups = true`로 NVIDIA 런타임의 cgroup 제어 자체를 비활성화(우회).
- **출처**: [NVIDIA/nvidia-container-toolkit#189](https://github.com/NVIDIA/nvidia-container-toolkit/issues/189) — GitHub 이슈, 2022-02-25

### SELinux AVC 거부로 `/dev/nvidiactl` 접근 실패
- **문제 상황**: `Failed to initialize NVML: Insufficient Permissions`. `ausearch -m avc`에 `denied { getattr } for ... comm="nvidia-smi" path="/dev/nvidiactl"` 기록.
- **원인**: SELinux가 NVIDIA 장치 노드를 `xserver_misc_device_t`로 라벨링하는데, 컨테이너 프로세스(`container_t`)는 기본 정책상 이 타입에 접근 권한이 없음.
- **해결/우회**: SELinux를 끄는 대신 `semanage boolean -m --on container_use_xserver_devices`로 해당 부울린만 활성화. RPM Fusion/COPR의 nvidia-container-toolkit SELinux 정책 패키지를 함께 설치 권장.
- **출처**: [Fedora Discussion](https://discussion.fedoraproject.org/t/how-to-use-nvidia-container-toolkit-without-disabling-selinux/125970) — 포럼, 2024-07 (해결 코멘트 2025-12)

### LDAP 매핑 사용자에서만 GPU 컨테이너 실행 실패 (user namespace 이슈)
- **문제 상황**: 로컬 사용자(UID 1001)는 정상 동작하지만, LDAP로 매핑된 사용자(UID 246740)는 `OCI runtime error: error executing hook '/usr/bin/nvidia-container-runtime-hook' (exit code: 1)`로 실패.
- **원인**: 레거시 `nvidia-container-runtime-hook` 방식이 non-local(LDAP/SSSD) 계정의 사용자 네임스페이스(subuid/subgid) 매핑을 정상적으로 해석하지 못함.
- **해결/우회**: Podman 메인테이너가 레거시 훅 대신 **CDI 방식**을 명시적으로 권고 — CDI는 사용자 네임스페이스 매핑 문제에서 자유로움. 저축은행 시나리오처럼 `llmsvc` 로컬 서비스 계정을 쓴다면 해당 없지만, 사용자 개인 AD 계정으로 GPU 컨테이너를 직접 돌리게 하는 구조라면 반드시 확인할 것.
- **출처**: [containers/podman Discussion #19681](https://github.com/containers/podman/discussions/19681) — GitHub 디스커션, 2023-08

### Quadlet 컨테이너가 재부팅 직후에는 자동 기동 실패 (네트워크 타이밍)
- **문제 상황**: Podman 5 환경에서 Quadlet 컨테이너가 부팅 시 자동 시작되지 않음. `systemctl --user start <name>.service`로 수동 실행하면 정상.
- **원인**: 부팅 초기 pasta 네트워크 인터페이스가 아직 준비되지 않아 "External interface not usable" 타이밍 이슈 발생.
- **해결/우회**: Quadlet 유닛에 `After=network-online.target`, `Wants=network-online.target`을 명시하고 최신 Podman으로 업그레이드. EP07의 `.container` 파일 예시에는 이 지시자가 빠져 있으므로 실제 적용 시 추가 검토 필요.
- **출처**: [containers/podman#22197](https://github.com/containers/podman/issues/22197) — GitHub 이슈, 2024-03-28

### CUDA 디바이스 인덱스와 `nvidia-smi` 순서 불일치
- **문제 상황**: 멀티 GPU 서버에서 CUDA가 인식하는 GPU 순서와 `nvidia-smi` 표시 순서가 달라 워크로드가 의도치 않은 GPU에 배치됨.
- **원인**: CUDA는 기본적으로 `FASTEST_FIRST` 휴리스틱으로 순서를 정하는 반면 `nvidia-smi`는 PCI 버스 ID 순서로 표시 — 동일 모델 GPU 3장이어도 PCIe 슬롯 배치에 따라 어긋날 수 있음.
- **해결/우회**: 환경변수 `CUDA_DEVICE_ORDER=PCI_BUS_ID`를 명시적으로 설정. `--tensor-parallel-size 3`처럼 여러 GPU를 특정 순서로 묶는 배포에서는 이 값을 고정하지 않으면 재부팅마다 GPU 배치가 흔들릴 수 있음.
- **출처**: [gpustack/gpustack#1633](https://github.com/gpustack/gpustack/issues/1633) — GitHub 이슈; [NVIDIA CUDA 환경변수 공식 문서](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html)

### 드라이버 업데이트 후 "Driver/library version mismatch"
- **문제 상황**: 커널 드라이버 업데이트 후 `nvidia-smi` 실행 시 `Failed to initialize NVML: Driver/library version mismatch`. 컨테이너 런타임은 정상인데 GPU 인식이 전면 실패.
- **원인**: 호스트 커널에 로드된 NVIDIA 커널 모듈 버전과 사용자 공간 라이브러리(`libnvidia-ml.so`) 버전 불일치 — 보통 드라이버 업그레이드 후 재부팅(커널 모듈 재적재)이 누락됐을 때 발생.
- **해결/우회**: 드라이버 패키지 완전 재설치 또는 재부팅. 폐쇄망에서는 반입 주기 사이에 호스트가 패치되면서 드라이버·CUDA 버전이 서서히 드리프트할 수 있어, 정기 점검 항목으로 삼을 것.
- **출처**: [NVIDIA/nvidia-container-toolkit#394](https://github.com/NVIDIA/nvidia-container-toolkit/issues/394), [#171](https://github.com/NVIDIA/nvidia-container-toolkit/issues/171) — GitHub 이슈

### rootful GPU 컨테이너 예외 운영 시 보안 강화 방법 (공식 가이드)
- **문제 상황**: EP08처럼 vLLM 컨테이너만 부득이하게 rootful로 운영할 때, 나머지 rootless 환경과 동일한 격리 수준을 어떻게 확보할지.
- **해결/우회 (모범 사례)**: Red Hat 공식 가이드는 (1) `--cap-drop=ALL` 후 필요한 capability만 `--cap-add`, (2) `--security-opt=no-new-privileges`로 권한 상승 차단, (3) 커스텀 SELinux 정책(`nvidia_container_t` 등 전용 타입), (4) 가능하면 컨테이너 엔진만 rootful이고 프로세스는 `--user`로 비루트 실행하는 조합을 권장. EP08의 "위험을 인지하고 보완 통제로 감싼다" 방향과 정확히 일치하는 공식 근거.
- **출처**: [Red Hat 공식 블로그 - GPU on bare metal RHEL 8](https://www.redhat.com/en/blog/how-use-gpus-containers-bare-metal-rhel-8); [Red Hat Developer - SELinux container labeling](https://developers.redhat.com/articles/2025/04/11/my-advice-selinux-container-labeling) — 2025-04-11

### SELinux 볼륨 라벨링 — `label=disable` 대신 쓸 수 있는 단계별 대안
- **문제 상황**: 모델 가중치·캐시 디렉토리 마운트 시 SELinux 컨텍스트 불일치로 파일을 못 읽어, `--security-opt=label=disable`로 임시 우회하는 경우가 많음(EP08도 이 옵션 사용) — 이는 SELinux 격리를 사실상 꺼버리는 선택.
- **해결/우회**: 단일 컨테이너 전용 볼륨은 `:Z`(전용 재라벨링), 여러 컨테이너 공유 볼륨은 `:z`(공유 재라벨링) 사용(EP07 Quadlet 예시가 이미 이 방식). 반복 접근하는 시스템 디렉토리는 `semanage fcontext -a -t container_file_t '/opt/models(/.*)?'; restorecon -Rv /opt/models`로 영구 컨텍스트 등록하는 편이 `label=disable`보다 안전.
- **출처**: [Red Hat Developer - SELinux container labeling](https://developers.redhat.com/articles/2025/04/11/my-advice-selinux-container-labeling), 2025-04-11

## 2. V100(Volta) 양자화·커널 호환성

EP03·EP04에서는 "AWQ가 V100(compute capability 7.0)에서 안 돌아서 GPTQ로 우회"까지 다뤘습니다. 실제로는 V100이 최신 서빙 스택 전반에서 훨씬 광범위하게 배제되고 있습니다.

### vLLM 0.20 이상부터는 V100이 아예 빌드 대상에서 제외됨
- **문제 상황**: vLLM 0.20.0 이상을 V100에 설치하면 CUDA 버전을 낮춰도 `CUDA error: no kernel image is available for execution on the device`로 아예 실행 불가.
- **원인**: vLLM 0.20.0부터 PyTorch 2.11+/CUDA 12.8+ 기본 빌드 타겟에서 sm_70(Volta)이 완전히 제외됨. CUDA 버전 문제가 아니라 vLLM 자체의 빌드 아키텍처 목록 문제.
- **해결/우회**: vLLM 0.18.x 이하로 고정하거나 `TORCH_CUDA_ARCH_LIST=7.0`으로 계속 소스 재빌드(EP04·EP08 방식). **최신 vLLM 기능이 필요해지는 시점이 곧 V100의 실질적 수명 종료 시점**이라는 걸 시사 — EP18에서 "전사 확대 시 A100 증설" 판단의 기술적 근거로 인용할 만함.
- **출처**: [vLLM 공식 포럼](https://discuss.vllm.ai/t/support-for-v100-sm-70-on-vllm-0-20/2605) — 공식 포럼

### bfloat16이 V100에서 하드웨어 자체 미지원 — `--dtype=half` 필수
- **문제 상황**: 옵션 없이 vLLM 서버를 기동하면 `Bfloat16 is only supported on GPUs with compute capability of at least 8.0. Your Tesla V100... has compute capability 7.0.`로 즉시 크래시.
- **원인**: 모델 config 기본 dtype(BF16)을 그대로 따라가려 하는데, BF16 텐서코어 연산은 Ampere(8.0+)부터 하드웨어 지원.
- **해결/우회**: 실행 커맨드에 `--dtype=half`(FP16)를 반드시 명시. EP08 실행 예시에는 이 옵션이 빠져 있어, 실제 적용 시 추가 필요.
- **출처**: [transformerlab/transformerlab-app#370](https://github.com/transformerlab/transformerlab-app/issues/370) — GitHub 이슈

### Marlin·FP8·INT8(W8A8)도 V100에서 공식 미지원 — 지원 매트릭스로 사전 확인
- **문제 상황**: GPTQ Int4로 우회했더라도 최신 vLLM 최적화 경로인 Marlin 커널로 자동 승격되지 않고 항상 느린 legacy GPTQ 커널로 고정 실행됨.
- **원인**: vLLM 공식 문서 기준 Volta(SM 7.0)는 GPTQ·BitBLAS(GPTQ)·bitsandbytes·DeepSpeedFP·GGUF만 지원하고 Marlin·AWQ·FP8(W8A8)·INT8(W8A8)은 전부 미지원.
- **해결/우회**: Marlin/FP8급 속도를 기대하지 말고 처음부터 GPTQ(non-Marlin) 또는 GGUF를 1순위로 설계. 이 지원 매트릭스를 배포 전 체크리스트에 넣으면 "왜 이렇게 느리지"로 며칠 날리는 일을 예방 가능.
- **출처**: [vLLM 공식 문서 - Supported Hardware for Quantization Kernels](https://docs.vllm.ai/en/v0.10.1/features/quantization/supported_hardware.html)

### bitsandbytes INT8도 V100에서 사실상 미지원
- **문제 상황**: bitsandbytes로 8bit 양자화 로딩 시 동작은 하지만 속도가 매우 느리거나 품질 저하.
- **원인**: HuggingFace 공식 문서에 "LLM.int8()는 Turing(RTX 20/T4) 또는 Ampere 이상 필요"라고 명시 — Volta는 최적화된 INT8 텐서코어 경로를 못 타고 비효율적 폴백 경로로 동작.
- **해결/우회**: V100에서는 bitsandbytes INT8/NF4 대신 GPTQ Int4나 GGUF Q4_K_M 사용.
- **출처**: [HuggingFace 공식 문서 - Bitsandbytes](https://huggingface.co/docs/transformers/v4.46.0/quantization/bitsandbytes)

### Qwen3 MoE 계열은 V100에서 V100 전용 튜닝 설정 파일이 없어 비최적 동작 + LLVM 컴파일 에러
- **문제 상황**: 4×V100에서 Qwen3-30B-A3B(MoE) 구동 시 `LLVM ERROR: Failed to compute parent layout for slice layout.` 발생.
- **원인**: (1) compute capability 8.0 미만은 V1 엔진 대신 레거시 V0 엔진으로 강제 폴백, (2) `Config file not found ... device_name=Tesla_V100-PCIE-32GB.json` — V100 전용 fused-MoE 튜닝 파일이 vLLM 배포판에 없어 비최적 기본 설정으로 동작, (3) FlashAttention2 미지원으로 XFormers 백엔드 전환 중 컴파일 실패.
- **해결/우회**: `benchmark_moe.py`로 V100 전용 MoE config를 직접 생성해 `fused_moe/configs/`에 저장. 여의치 않으면 tensor-parallel-size를 줄이거나 MoE가 아닌 dense 모델(Qwen2.5-32B처럼)로 우회 — 저축은행 시나리오가 애초에 dense 모델을 고른 게 결과적으로 이 함정을 피한 선택이었음.
- **출처**: [QwenLM/Qwen3#1294](https://github.com/QwenLM/Qwen3/issues/1294), [vllm-project/vllm#17392](https://github.com/vllm-project/vllm/issues/17392) — GitHub 이슈

### AWQ를 GPU 없는 Docker 빌드 환경에서 소스 빌드하면 컴파일 자체가 실패
- **문제 상황**: Docker 빌드 컨테이너(실 GPU 없음)에서 AWQ 소스 빌드 시 `Feature 'ldmatrix' requires .target sm_75 or higher` 컴파일 에러.
- **원인**: GPU 미검출 상태에서 AWQ CUDA 커널이 기본값(compute_70)으로 컴파일을 시도하며 sm_75/sm_80 전용 PTX 명령어를 sm_70 타겟에 끼워 넣어 실패 — AWQ 커널 자체가 V100에서 근본적으로 성립하지 않음을 재확인시켜주는 사례.
- **해결/우회**: 애초에 AWQ 빌드를 시도하지 말고 GPTQ/GGUF로 전환(EP03·EP04와 동일 결론).
- **출처**: [vllm-project/vllm#1070](https://github.com/vllm-project/vllm/issues/1070) — GitHub 이슈

### 실전 3×V100 32GB 벤치마크 수치 (Qwen2.5 계열)
- **참고 자료**: 3×V100 32GB에서 Qwen2.5-7B/14B, Gemma3-4B/12B를 FP16으로 서빙한 벤치마크. 동시 요청 50개 기준 최고 1,847.72 tok/s(Gemma3-4B) ~ 최저 449.39 tok/s(Gemma3-12B). EP08의 Qwen2.5-32B 벤치마크(첫 토큰 1.8초)를 검증할 때 비교 기준점으로 참고할 수 있음 — 단 32B급 자체 벤치마크는 이 자료에 없어 직접 실측 보완이 필요.
- **출처**: [DatabaseMart - 3×V100 vLLM Benchmark](https://www.databasemart.com/blog/vllm-gpu-benchmark-v100-3) — 벤치마크 블로그

### V100에서는 vLLM 외 서빙 엔진(TGI, TensorRT-LLM, Triton)이 전부 거부됨
- **문제 상황**: 동일 V100 환경에서 TGI·TensorRT-LLM·Triton Inference Server 최신 버전은 모두 `CUDA error: no kernel image available for sm_70`로 초기화 자체가 거부됨.
- **원인**: 세 엔진 모두 최신 빌드에서 Volta를 빌드 타겟에서 제외.
- **해결/우회**: V100에서는 vLLM(V0 엔진, FP16, 2장 이상 텐서 병렬)이 사실상 유일한 선택지 — EP08의 "vLLM을 소스에서 직접 빌드" 결정이 대안이 없어 불가피했던 선택이었음을 뒷받침. 같은 벤치마크에서 Llama-2-70B는 4장으로도 OOM으로 실패해, **V100 3장 구성에서 32B가 사실상 상한선**이라는 게 실측으로 확인됨.
- **출처**: [E2E Networks - A30 vs V100 LLM Inference Benchmark](https://www.e2enetworks.com/blog/NVIDIA-a30-vs-v100-for-llM-inference-vllm-tgi-tensorrt-llm-benchmark-7B-70B-Models.md) — 벤치마크 블로그

### (참고용, 비공식) 커뮤니티가 V100 전용 AWQ 커널을 직접 포크로 구현한 사례
- **내용**: 1CatAI/1Cat-vLLM, humanjesse/vllm-v100 등은 vLLM을 포크해 V100 전용 AWQ GEMM 커널(`awq_gemm_sm70`)을 직접 작성, `min_capability`를 75→70으로 낮춘 패치를 적용. GPTQ Triton 커널(오차율 약 2%) 대신 AWQ 경로(오차율 0.1% 미만)를 씀. 단 V100 Triton JIT 첫 컴파일에 30~90분이 걸려 `VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS=3000` 설정이 필요했고, `--disable-custom-all-reduce`도 필수였다고 기록됨.
- **판단**: 프로덕션에 권장하긴 어려운 비공식 포크지만 "AWQ가 V100에서 막힌 이유"와 "GPTQ 외에 존재하는 유일한 대안 경로"를 보여주는 참고 사례.
- **출처**: [humanjesse/vllm-v100 README](https://github.com/humanjesse/vllm-v100/blob/main/README.md), [1CatAI/1Cat-vLLM](https://github.com/1CatAI/1Cat-vLLM) — 비공식 커뮤니티 포크

## 3. vLLM 멀티 GPU 배포

EP08에서 `--tensor-parallel-size 3`으로 V100 3장을 묶었고, EP14에서 새 모델을 병행 기동, EP17에서 동일 GPU에 두 번째 vLLM 인스턴스를 얹었습니다. 이 세 가지 패턴 모두에서 실전 이슈가 보고돼 있습니다.

### TP 크기가 어텐션 헤드 수로 나눠떨어지지 않으면 기동 자체가 실패
- **문제 상황**: `ValueError: Total number of attention heads (52) must be divisible by tensor parallel size (3).` 유형 에러가 다양한 모델·GPU 조합에서 반복 보고됨.
- **원인**: vLLM은 텐서 병렬화 시 어텐션 헤드를 GPU 수만큼 균등 분할해야 하는데, 최신 모델은 2의 거듭제곱이 아닌 헤드 수(Qwen2-7B는 28개)를 갖는 경우가 많아 홀수 GPU 대수와 충돌하기 쉬움.
- **해결/우회**: **모델 채택 전에 헤드 수를 확인해 TP=3으로 나눠떨어지는지 먼저 검증**할 것 — Qwen2.5-32B-Instruct는 헤드 수가 3으로 나눠떨어져 EP03·EP08에서 문제없이 넘어갔지만, 이건 우연이 아니라 사전에 확인했어야 할 조건. 다음에 모델을 바꿀 때(EP14 시나리오) 반드시 재확인 필요.
- **출처**: [vllm-project/vllm#414](https://github.com/vllm-project/vllm/issues/414), [#2652](https://github.com/vllm-project/vllm/issues/2652), [#4232](https://github.com/vllm-project/vllm/issues/4232) — GitHub 이슈

### CUDA 그래프 캡처 중 NCCL "invalid usage" 에러
- **문제 상황**: 멀티 GPU TP 활성화 상태에서 `RuntimeError: NCCL error: invalid usage`와 함께 CUDA 그래프 캡처 관련 경고 발생.
- **원인**: 모델 워밍업 단계의 CUDA 그래프 캡처 과정에서 NCCL 통신 연산이 그래프에 포함되며 특정 드라이버·CUDA 버전 조합에서 불안정해짐.
- **해결/우회**: `enforce_eager=True`로 CUDA 그래프 캡처를 건너뛰어 우회(성능은 다소 하락).
- **출처**: [vllm-project/vllm#7201](https://github.com/vllm-project/vllm/issues/7201) — GitHub 이슈

### 동일 GPU에 두 번째 vLLM 인스턴스를 띄우면 음수 KV 캐시 크기로 기동 실패
- **문제 상황**: EP17처럼 동일 GPU에 소형 모델을 두 번째 인스턴스로 얹을 때, `ValueError: No available memory for the cache blocks.` 발생. 프로파일링 로그에 `kv_cache_size=-53.60GiB`처럼 **음수** 값이 찍힘.
- **원인**: vLLM의 메모리 프로파일링 로직이 "이미 실행 중인 다른 vLLM 프로세스가 점유한 VRAM"까지 자기 자신의 기준선 계산에 잘못 포함시켜, 가용 KV 캐시가 음수로 계산됨. v0.6.4.post1부터 나타난 회귀로 보고됨.
- **해결/우회**: 공식 수정 없음("not planned"로 종료). 실무에서는 각 인스턴스의 `--gpu-memory-utilization`을 사전에 보수적으로 고정 배분(EP17이 32B는 0.75, 코더 모델은 0.10으로 나눈 것과 같은 방향)하고, 두 인스턴스를 **동시에** 기동해 프로파일링 값이 서로를 침범하지 않는지 검증할 것. EP17 절차를 그대로 따르되, 기동 순서·타이밍까지 재현성 있게 스크립트화해두는 걸 권장.
- **출처**: [vllm-project/vllm#10533](https://github.com/vllm-project/vllm/issues/10533), [#10643](https://github.com/vllm-project/vllm/issues/10643) — GitHub 이슈

### PCIe 전용 연결(NVLink 없음)에서 TP 사용 시 통신 오버헤드로 오히려 성능 역행
- **문제 상황**: 멀티 GPU 서버에서 TP=1(미적용)로 서빙 시 GPU 1장 단독보다 오히려 처리량이 절반 이하로 떨어진 사례(3,965 → 1,796 tok/s).
- **원인**: TP=1이라도 GPU마다 별도 CUDA 컨텍스트가 초기화되며, PCIe 전용 연결(V100처럼 NVLink 없는 구성, `nvidia-smi topo -m`에서 SYS로 표시)은 NVLink 대비 대역폭이 훨씬 낮아(PCIe ~32GB/s vs NVLink ~300GB/s) 레이어마다 발생하는 all-reduce 통신 비용이 커짐. PCIe 전용 TP는 스케일링 효율이 0.70~0.78배 수준.
- **해결/우회**: 배포 전 `nvidia-smi topo -m`으로 V100 3장의 실제 인터커넥트를 확인할 것 — NVLink가 아니라면 이 통신 비용이 EP08 벤치마크(TP=3, 첫 토큰 1.8초)에 이미 반영돼 있는 수치인지, 트래픽이 늘어날 때도 유지될지 별도 검증 필요.
- **출처**: [DatabaseMart - vLLM Optimization Guide](https://www.databasemart.com/blog/vllm-distributed-inference-optimization-guide) — 벤더 기술 블로그

### 긴 컨텍스트 요청 시 VRAM이 충분해 보여도 KV 캐시 부족으로 기동 실패
- **문제 상황**: `ValueError: To serve at least one request with the model's max seq len (262144), 27.45 GiB KV cache is needed, but only 23.43 GiB is available.` — VRAM 총량은 넉넉해 보이는데 초기화 자체가 실패.
- **원인**: KV 캐시 필요량은 `max_model_len × 배치 관련 파라미터`에 비례해 증가하며, `gpu_memory_utilization`이 허용한 가용 메모리보다 최대 시퀀스 길이가 요구하는 KV 캐시가 크면 기동이 막힘.
- **해결/우회**: `gpu_memory_utilization`을 높이거나(공유 중이면 한계 있음), `max_model_len`을 실제 업무에 필요한 수준으로 제한. EP08은 `--max-model-len 8192`로 이미 보수적으로 잡아뒀지만, EP17에서 두 번째 모델과 VRAM을 나눠 쓰게 된 이후(`--gpu-memory-utilization 0.75`로 하향)에는 이 여유가 줄었으므로 재검증 필요.
- **출처**: [vllm-project/vllm#37951](https://github.com/vllm-project/vllm/issues/37951) — GitHub 이슈

### 에어갭 환경에서 로컬 캐시가 있어도 Hugging Face 접근을 시도해 실패
- **문제 상황**: 로컬에 모델 가중치를 전부 받아둔 상태로 기동해도 `Cannot access gated repo for url https://huggingface.co/...` 에러로 실패. `HF_HUB_OFFLINE=1`을 설정하면 다운로드 시도는 막히지만 이번엔 "파일을 찾을 수 없음"으로 크래시하는 사례도 있음(Gemma 계열에서 특히 재현).
- **원인**: 모델 로딩 경로가 Hugging Face Hub의 캐시 디렉토리 구조(스냅샷 해시, `refs/main` 등)를 그대로 기대하는데, 단순히 safetensors 파일만 복사해오면 "로컬에 파일이 있음"과 "허브 캐시 규격에 맞게 배치됨"이 다른 문제로 취급됨.
- **해결/우회**: 온라인 호스트에서 `huggingface-cli download`(또는 `snapshot_download`)로 받은 **허브 캐시 레이아웃을 그대로 유지**한 채 반입. 서빙 시 로컬 디렉터리 경로를 직접 지정하고 `HF_HUB_OFFLINE=1`+`TRANSFORMERS_OFFLINE=1`을 함께 설정. **완전 폐쇄망(네트워크 네임스페이스까지 차단)에서 사전 리허설 기동을 반드시 거칠 것** — EP08은 GPTQ 체크포인트를 로컬 디렉터리로 직접 지정해 이 문제를 우회하는 구조지만, 원본 FP16을 그대로 쓰는 경로(EP14의 새 모델 반입 등)에서는 재현 가능성이 있음.
- **출처**: [vllm-project/vllm#9255](https://github.com/vllm-project/vllm/issues/9255), [#39039](https://github.com/vllm-project/vllm/issues/39039) — GitHub 이슈

### Sleep Mode를 활용한 무중단 모델 교체 — EP14 방식의 대안
- **참고 자료**: EP14는 신·구 모델을 동시에 올릴 VRAM이 부족해 "야간에 기존 모델을 잠시 내리고 검증"하는 방식을 택했습니다. vLLM의 Sleep Mode(`/sleep`, `/wake_up` API)를 쓰면 Level 1(가중치를 CPU RAM으로 오프로드)은 대형 모델 기준 3~6초 만에 깨어나 완전 재기동 대비 최대 200배 빠릅니다.
- **제약**: 이 관리용 엔드포인트는 `VLLM_SERVER_DEV_MODE=1`이 필요하고 신뢰된 내부망에서만 노출해야 하며(외부 노출 시 서비스 중단 위험), 깨어난 직후 워밍업을 생략하면 첫 추론이 최대 5.8배 느려짐 — 저축은행처럼 완전히 격리된 내부망(`airgap-net`)에서만 노출한다는 조건을 지키면 EP14의 "야간 검증" 절차를 자동화하는 데 쓸 수 있는 옵션.
- **출처**: [vLLM 공식 블로그 - Sleep Mode](https://vllm.ai/blog/2025-10-26-sleep-mode), [vLLM 공식 문서 - Sleep Mode](https://docs.vllm.ai/en/latest/features/sleep_mode/)

## 4. LiteLLM 게이트웨이

EP05·EP10에서 스트리밍 버퍼링 문제와 팀별 가상 키 관리까지 다뤘습니다. LiteLLM을 실제로 프로덕션에서 운영한 사례들은 그 외에도 DB 연결·캐시 일관성 관련 문제를 다수 보고합니다.

### RDS/Postgres가 유휴 커넥션을 조용히 끊어 간헐적 500 에러
- **문제 상황**: 중간 트래픽에서 간헐적으로 약 50% 요청이 `Error in PostgreSQL connection: Error { kind: Closed, cause: None }`로 실패. 재시도하면 성공하지만 레이턴시가 튐.
- **원인**: DB가 일정 시간 유휴 상태인 TCP 커넥션을 조용히 끊는데, LiteLLM이 쓰는 Prisma/Quaint 드라이버가 풀 안의 커넥션 상태를 검증하지 않고 재사용. `DATABASE_URL`에 유휴 커넥션 수명 기본값이 없어 DB 타임아웃보다 오래 방치됨.
- **해결/우회**: `DATABASE_URL`에 `max_idle_connection_lifetime=60`(DB가 끊기 전에 LiteLLM이 먼저 정리), `socket_timeout=10`(죽은 커넥션을 빠르게 감지) 추가. EP10의 Postgres 컨테이너 설정에는 이 파라미터가 없어, 운영 기간이 길어지면 재현될 수 있음.
- **출처**: [BerriAI/litellm#22289](https://github.com/BerriAI/litellm/issues/22289) — GitHub 이슈

### 가상 키 업데이트가 캐시 재소생(resurrection)으로 무기한 무시됨
- **문제 상황**: `/key/update`로 팀 예산·모델 목록을 변경해도 부하가 있으면 조용히 무시됨. 여러 인스턴스를 운영하면 한 인스턴스에서만 반영되고 나머지는 계속 옛 설정 사용.
- **원인**: `update_cache()`가 캐시된 키 객체를 읽어 spend 필드만 수정해 재저장하는 read-modify-write를 수행하는데, 이 write가 `/key/update`로 인한 무효화 이후 비동기 실행되면 옛 객체를 다시 덮어씀. 인스턴스마다 독립적인 캐시라 크로스 인스턴스 무효화가 안 됨.
- **해결/우회**: 공식 수정 없음. 예산·차단 반영이 지연될 수 있음을 감안해 EP05·EP10에서 팀 예산을 변경한 뒤에는 일정 시간 후 재확인할 것 — 지금은 단일 인스턴스 구성이라 위험이 낮지만, EP18에서 예고된 전사 확대(레플리카 증설) 시점에 특히 주의.
- **출처**: [BerriAI/litellm#25553](https://github.com/BerriAI/litellm/issues/25553) — GitHub 이슈, 2026-04

### 전역 예산 제한(`max_budget`)이 콜백 미등록으로 완전히 우회되는 버그
- **문제 상황**: `litellm_settings.max_budget`을 아주 작은 값으로 설정해도 프록시가 예산 초과 요청을 계속 처리.
- **원인**: 예산 제한 객체가 생성만 되고 실제 콜백 시스템에 등록되지 않아 요청 차단 훅이 호출되지 않는 구조적 버그(v1.83.10 기준).
- **해결/우회**: 전역 `litellm_settings.max_budget`에만 의존하지 말 것. EP05·EP10처럼 **팀별/키별 `max_budget`(가상 키 단위)**이 실제로 집행되는지 별도로 검증할 것 — 이 문서 시나리오는 애초에 전역이 아니라 가상 키 단위로 예산을 나눠서 이 버그의 영향권 밖일 가능성이 높지만, 확인은 필요.
- **출처**: [BerriAI/litellm#27381](https://github.com/BerriAI/litellm/issues/27381) — GitHub 이슈, 2026-05

### Docker 태그 업그레이드 후 DB 연결이 완전히 끊긴 채 복구 안 됨
- **문제 상황**: `main-v1.80.8-stable`에서 `main-v1.81.0-stable`로 업그레이드하자 DB 연결이 끊긴 채 복구 안 됨. `main-v1.80.8-stable`로 롤백하면 정상화.
- **원인**: 마이그레이션은 정상 종료되지만 이후 Prisma 쿼리 엔진이 커넥션을 재수립하지 못하는 버전 간 회귀로 추정.
- **해결/우회**: `main-stable`·`main-latest` 같은 롤링 태그 대신 **특정 `vX.Y.Z` 태그로 고정**. EP04는 `ghcr.io/berriai/litellm:main-stable`을 그대로 반입하고 있어, 분기별 재양자화·재반입(EP06) 시점마다 이 위험에 새로 노출됨 — 다음 반입부터는 태그를 고정하고 스테이징에서 먼저 업그레이드 리허설을 거칠 것을 권장.
- **출처**: [BerriAI/litellm#19773](https://github.com/BerriAI/litellm/issues/19773) — GitHub 이슈, 2026-01

### `background_health_checks: true` 설정 시 기동 자체가 무한 대기
- **문제 상황**: config.yaml에서 `background_health_checks: true`를 켜면 "Application startup complete"에 도달하지 못하고 CPU 100%로 무한 대기, SIGKILL로만 종료 가능.
- **원인**: 명확히 특정되지 않았으나 백그라운드 헬스체크 초기화와 DB 커넥션 수립 로직 간 교착으로 추정.
- **해결/우회**: 프로덕션에서는 이 옵션을 끄고, 모델 헬스체크가 필요하면 외부 스케줄러로 `/health` 엔드포인트를 별도 호출.
- **출처**: [BerriAI/litellm#10114](https://github.com/BerriAI/litellm/issues/10114) — GitHub 이슈, v1.66.2

### 프록시를 거치면서 vLLM 대비 처리량이 최대 4배까지 저하
- **문제 상황**: 프록시 경유 시 GPU 직접 호출 대비 초당 요청 처리량이 최대 4배까지 떨어진 사례. 원인이 근본적으로 규명되지 않은 채 남아있음.
- **관련 공식 가이드**: `LITELLM_LOG=INFO`(DEBUG 금지), `MAX_PAYLOAD_SIZE_FOR_DEBUG_LOG`, `MAX_BASE64_LENGTH_FOR_LOGGING` 설정으로 로깅 오버헤드를 줄이고, 응답 헤더의 `x-litellm-overhead-duration-ms`로 병목 구간을 구분할 것을 권장.
- **해결/우회**: EP13에서 "챗봇이 느려요" 장애를 KV 캐시 관점에서만 진단했는데, 게이트웨이 자체 오버헤드도 별도 원인일 수 있음을 시사 — 다음 장애 대응 시 `x-litellm-overhead-duration-ms` 헤더를 진단 항목에 추가할 만함.
- **출처**: [BerriAI/litellm#21046](https://github.com/BerriAI/litellm/issues/21046) — GitHub 이슈, 2026-02; [공식 문서 - Latency Overhead Troubleshooting](https://docs.litellm.ai/docs/troubleshoot/latency_overhead)

### 프로덕션 배포 DB 커넥션 풀 사이징 공식 권장값
- **참고 자료(모범 사례)**: `general_settings.database_connection_pool_limit: 10`으로 워커당 커넥션 상한 지정, 1000 req/s 이상에서는 Redis 기반 트랜잭션 버퍼로 spend 업데이트를 큐잉해 DB 데드락 방지, 멀티 인스턴스 시 Redis 7.0+로 레이트리밋·라우터 상태 공유. EP18에서 예고한 전사 확대(레플리카 증설) 시점에 미리 검토해둘 항목.
- **출처**: [공식 문서 - Production Best Practices](https://docs.litellm.ai/docs/proxy/prod), [공식 문서 - High Availability Setup](https://docs.litellm.ai/docs/proxy/db_deadlocks)

### `hosted_vllm/` 프리픽스 강제로 인한 모델 이름 매핑 혼란
- **문제 상황**: self-hosted vLLM을 연결하려면 `litellm_params.model`을 `hosted_vllm/<실제_모델명>` 형태로 프리픽스를 붙여야 하는데, 채팅뿐 아니라 임베딩·리랭크 엔드포인트까지 동일하게 요구돼 혼란을 유발.
- **해결/우회**: `model_name`(클라이언트 노출용 별칭)과 `litellm_params.model: openai/<실제모델명>`(백엔드 호출용, EP05가 실제로 쓴 `openai/` 프리픽스 방식)을 명확히 분리해 매핑. EP05는 `openai/` 프리픽스를 써서 이 문제를 우회한 셈이지만, provider 스타일을 바꿀 일이 있다면 프리픽스 규칙을 재확인할 것.
- **출처**: [BerriAI/litellm#12934](https://github.com/BerriAI/litellm/issues/12934) — GitHub 이슈, 2025-07

### nginx SSE 스트리밍 — 버퍼링 외에도 HTTP/1.0·타임아웃 문제 존재
- **문제 상황**: `proxy_buffering off`(EP10이 이미 적용)만으로는 완전히 해결 안 되는 경우가 있음 — nginx의 `proxy_http_version` 기본값이 1.0인데, HTTP/1.0은 청크 전송 인코딩을 지원하지 않아 스트리밍이 여전히 무력화됨. `proxy_read_timeout` 기본값 60초도 긴 생성 요청 도중 연결이 끊기는 원인이 됨.
- **해결/우회**: `proxy_http_version 1.1; proxy_set_header Connection ''; proxy_read_timeout 86400s;`를 `proxy_buffering off`와 함께 설정. EP10의 nginx 설정 예시(`proxy_buffering off; proxy_read_timeout 300s;`)에 `proxy_http_version 1.1`이 빠져 있고 `proxy_read_timeout`도 300초로 EP13에서 다뤘던 초장문 요청(80페이지 PDF)엔 짧을 수 있어 재검토 여지가 있음.
- **출처**: [oneuptime.com - SSE Through Nginx](https://oneuptime.com/blog/post/2025-12-16-server-sent-events-nginx/view), [getpagespeed.com - Nginx Reverse Proxy Ollama/vLLM](https://www.getpagespeed.com/server-setup/nginx-reverse-proxy-ollama-vllm)

## 5. Ollama 오프라인 서빙

EP09에서 바이너리 반입과 아웃바운드 차단까지 다뤘습니다. Ollama를 임베딩 서빙용으로 실전 운영한 사례에서는 권한·버전·정확도 관련 문제가 추가로 보고됩니다.

### `OLLAMA_MODELS` 환경변수가 systemd 서비스에서 무시되거나 권한 오류
- **문제 상황**: systemd drop-in으로 `OLLAMA_MODELS` 경로를 지정해도 모델이 여전히 기본 경로에 저장되거나, `mkdir: permission denied` 에러.
- **원인**: 서비스가 전용 시스템 계정(EP09 예시의 `llmsvc`)으로 구동되는데, 그 계정이 지정 경로에 대한 소유권/쓰기 권한이 없음.
- **해결/우회**: 절대경로만 사용하고(`~` 축약 금지 — systemd는 셸처럼 확장하지 않음) `chown -R llmsvc:llmsvc <경로>`로 소유권을 명시적으로 부여한 뒤, 작은 모델로 실제 저장 위치를 검증.
- **출처**: [ollama/ollama#4454](https://github.com/ollama/ollama/issues/4454), [#2147](https://github.com/ollama/ollama/issues/2147) — GitHub 이슈

### GPU 디바이스 그룹 미포함으로 조용히 CPU 폴백
- **문제 상황**: 드라이버는 정상 설치돼 있고 `nvidia-smi`도 동작하는데, systemd로 구동한 Ollama가 CPU로만 추론.
- **원인**: 서비스 계정이 `video`/`render` 그룹에 속하지 않으면 GPU 디바이스 파일 접근이 막혀 조용히 CPU로 폴백됨(에러가 명확하게 안 뜨는 경우도 있음).
- **해결/우회**: `id llmsvc`로 그룹 소속 확인 후 `usermod -aG video,render llmsvc`로 추가. 디버깅 시 `sudo -u llmsvc ollama serve`로 systemd 로그 레이어를 거치지 않고 직접 실행해 원본 에러 확인.
- **출처**: [Ollama 공식 트러블슈팅 문서](https://docs.ollama.com/troubleshooting)

### BGE-M3 임베딩에서 특정 입력에 대해 NaN 출력
- **문제 상황**: 다량의 텍스트를 임베딩하던 중 일부 텍스트에서 `"error":"failed to encode response: json: unsupported value: NaN"`. 특정 토큰 조합/길이에서만 재현되는 예측 불가능한 패턴.
- **원인**: 명확히 규명되지 않았으나 이후 패치로 수정됨(내부 연산의 수치적 불안정성으로 추정).
- **해결/우회**: 최신 패치 버전으로 업그레이드. **폐쇄망에서는 업그레이드 전 사내 문서 샘플로 회귀 테스트를 거칠 것** — EP12의 주 1회 문서 반입 파이프라인이 대량 upsert를 자동화하고 있어, 이런 예외가 발생하면 파이프라인 전체가 중단될 수 있음.
- **출처**: [ollama/ollama#13572](https://github.com/ollama/ollama/issues/13572) — GitHub 이슈

### `truncate` 옵션이 무시되어 긴 입력에서 에러 (버전 리그레션)
- **문제 상황**: 임베딩 API 요청 시 `truncate: true`(기본값)를 둬도 무시되고 컨텍스트 길이 초과 시 에러 반환. 특정 버전(0.13.5)의 리그레션.
- **원인**: 이전 버전에서는 정상 동작하던 truncate 처리 로직이 특정 버전 업데이트에서 깨짐.
- **해결/우회**: 수정 버전으로 업그레이드하되, BGE-M3처럼 8192 토큰 컨텍스트를 가진 임베딩 모델을 쓸 경우 **애플리케이션 레벨(EP15의 청킹 단계)에서 사전에 입력을 자르는 방어적 처리**를 추가로 해둘 것 — EP15의 청킹은 400자 단위라 이 문제를 우회하고 있지만, 다른 워크로드에서 긴 텍스트를 직접 임베딩 API에 넘기는 경로가 생기면 재현 가능.
- **출처**: [ollama/ollama#14186](https://github.com/ollama/ollama/issues/14186) — GitHub 이슈

### 벡터DB 클라이언트가 BGE-M3의 실제 임베딩 차원(1024)을 인식 못하고 1536(OpenAI 기본값)으로 하드코딩
- **문제 상황**: 일부 RAG 프레임워크에서 임베딩 차원을 명시해도 벡터스토어 설정에 전파되지 않아 컬렉션이 OpenAI 기본값(1536차원)으로 생성되고 차원 불일치 에러 발생.
- **해결/우회**: EP15는 `VectorParams(size=1024, ...)`로 Qdrant 컬렉션 차원을 직접 지정해 이 문제를 원천적으로 피하고 있음 — 다만 다른 RAG 프레임워크나 라이브러리를 추가로 도입할 때는 임베딩 모델을 교체하거나 벡터DB를 새로 붙일 때마다 이 차원 값이 어디서 오는지 반드시 직접 확인할 것.
- **출처**: [mem0ai/mem0#4695](https://github.com/mem0ai/mem0/issues/4695) — GitHub 이슈, 2026-04

### Ollama 버전 업그레이드 후 이전에 등록된 GGUF 모델이 실행 실패
- **문제 상황**: 업그레이드 후 일부 GGUF 모델이 `error starting llama-server: llama-server binary not found` 또는 `llama runner process has terminated: exit status 2`로 실패.
- **원인**: 패키지 매니저 설치본에서 새 버전이 요구하는 바이너리가 예상 경로에 누락(배포 패키징 문제)되거나, 원인 미상의 런타임 에러.
- **해결/우회**: tar 아카이브 형태의 공식 릴리스(EP09 방식)를 사용하고, **업그레이드 전 스테이징 환경에서 기존 Modelfile/GGUF 조합에 대해 회귀 테스트**를 거칠 것 — EP09가 이미 tar 방식을 쓰고 있어 첫 번째 원인은 해당 없지만, 두 번째(원인 미상 런타임 에러)는 버전 업그레이드마다 검증이 필요.
- **출처**: [ollama/ollama#16417](https://github.com/ollama/ollama/issues/16417), [#12648](https://github.com/ollama/ollama/issues/12648) — GitHub 이슈

### systemd 프로덕션 하드닝 — 리소스 제한·재시작 정책·로그 로테이션
- **문제 상황**: 기본 유닛 파일은 메모리/CPU 상한이 없어 대형 모델 로드 시 무제한으로 메모리를 소비할 수 있고, 저널 로그도 무제한 누적됨.
- **참고 자료(모범 사례)**: drop-in override로 `MemoryHigh`/`MemoryMax` 설정(예: 시스템 메모리의 80%/93%), `Restart=on-failure`+`RestartSec=10`+`RestartMaxDelaySec=300`+`StartLimitBurst=5`로 재시작 루프 방지, `/etc/systemd/journald.conf.d/`에서 로그 보관 정책 설정, `NoNewPrivileges=true`+`ProtectSystem=strict`+`DeviceAllow=/dev/nvidia0 rw` 조합으로 샌드박싱. EP09의 유닛 파일에는 이런 하드닝이 없어, 운영 안정성 강화 시 참고할 만함.
- **출처**: [linuxprofessional.ie - Ollama Systemd Hardening](https://linuxprofessional.ie/article.php?slug=ollama-systemd-service-production-hardening) — 블로그(1차 소스 아님, 적용 전 자체 검증 권장)

## 6. Open WebUI + LDAP 연동

EP11에서 LDAP 연동과 그룹 매핑까지 다뤘습니다. 실전 LDAP/AD 연동 사례에서는 TLS·인증서·그룹 권한 관련 문제가 특히 많이 보고됩니다.

### LDAP TLS 비활성화 시 인증 자체가 실패
- **문제 상황**: TLS를 끄고 로그인 시도 시 인증이 즉시 실패.
- **원인**: 비-TLS 경로에서도 백엔드가 TLS 관련 클래스를 참조하는 조건 분기 오류.
- **해결/우회**: EP11은 애초에 `LDAP_USE_TLS=true`로 TLS를 켜고 있어 해당 없음 — 다만 이 문제가 있었다는 건 **TLS를 끄고 테스트하는 건 아예 선택지가 아니라는 뜻**이므로, 향후 트러블슈팅 시 "TLS를 잠깐 꺼서 원인을 좁혀보자"는 접근 자체를 피할 것.
- **출처**: [open-webui/open-webui#13064](https://github.com/open-webui/open-webui/issues/13064) — GitHub 이슈, 2025-04

### LDAP TLS 활성화 시 로컬 인증서 파일 경로가 강제로 요구됨 (공인 CA도 예외 없음)
- **문제 상황**: TLS를 켜고 인증서 경로를 비워두면 "TLS is enabled but certificate file path is missing"으로 저장 자체가 안 됨. 사내 LDAP 서버가 공인 CA 인증서를 쓰더라도 로컬 파일 경로를 강제로 요구.
- **해결/우회**: 사내 LDAP 서버 인증서를 파일로 저장해 경로를 채워야 함. EP11 설정 예시(`LDAP_USE_TLS=true`)에는 인증서 경로 지정이 빠져 있어, 실제 적용 시 이 값이 필수로 필요할 수 있음.
- **출처**: [open-webui/open-webui#12408](https://github.com/open-webui/open-webui/issues/12408) — GitHub 이슈, 2025-04

### 사내 CA(SSL 인터셉션) 환경에서 CERTIFICATE_VERIFY_FAILED — OAuth와 일반 API가 다른 환경변수 필요
- **문제 상황**: 사내 방화벽/프록시가 SSL을 가로채는 환경에서 `[SSL: CERTIFICATE_VERIFY_FAILED]`. OAuth 연동은 되는데 다른 API 호출은 실패하는 등 요청 종류마다 결과가 다름.
- **원인**: 컨테이너 이미지가 사내 루트 CA를 신뢰 저장소에 포함하지 않음. OAuth 요청은 `httpx`, 나머지는 `requests` 라이브러리를 써서 각각 다른 환경변수가 필요.
- **해결/우회**: 호스트의 CA 번들을 컨테이너에 read-only로 마운트하고 `REQUESTS_CA_BUNDLE`과 `SSL_CERT_FILE` **두 환경변수를 모두** 그 경로로 지정(하나만 설정하면 절반만 해결됨). 금융권처럼 SSL 인터셉션 프록시를 쓰는 망 구조라면 반드시 확인할 항목.
- **출처**: [open-webui/open-webui Discussion #9949](https://github.com/open-webui/open-webui/discussions/9949) — GitHub 디스커션

### mail 속성이 없는 AD 계정의 LDAP 로그인 거부
- **문제 상황**: AD 계정에 `mail` 속성이 비어 있으면 "Attribute for Mail"을 다른 필드로 지정해도 로그인이 거부됨. `ldapsearch`로는 동일 필터가 정상 반환됨.
- **원인**: LDAP 바인드 자체는 성공하지만, 사용자 레코드 생성 로직이 mail 속성 누락을 처리하지 못함(바인드 문제가 아니라 프로비저닝 로직 문제).
- **해결/우회**: 반입 전 사내 AD에서 실제 로그인 대상 계정(특히 현업팀·개발팀 전 인원)의 mail 속성이 채워져 있는지 사전 전수 확인 — EP11이 LDAP 그룹 매핑을 문서화했다고 했는데, 이 항목도 함께 점검 체크리스트에 추가할 만함.
- **출처**: [open-webui/open-webui#17682](https://github.com/open-webui/open-webui/issues/17682) — GitHub 이슈, 2025-09

### 그룹별 모델 권한이 "기본값"에 의해 무시됨 + 저장 후 원복되는 별도 버그
- **문제 상황**: (1) 그룹 단위로 모델 접근을 제한해도 워크스페이스 기본(default) 권한이 우선 적용돼 그룹 설정이 무시됨. (2) 모델 편집 화면에서 그룹을 지정해 저장해도(200 OK 반환) 새로고침하면 원래 상태로 되돌아가는 별도의 저장 버그도 보고됨.
- **해결/우회**: "기본 권한을 가장 제한적으로 설정한 뒤 그룹별로 허용을 추가"하는 방향으로 운영(기본 허용 후 그룹별 차단은 신뢰하지 않을 것). **EP11의 "LDAP 그룹 → WebUI 그룹 → LiteLLM team_id" 삼단 매핑에서 마지막 방어선을 LiteLLM 팀별 가상 키(EP05·EP10)에 두는 게 안전** — Open WebUI 그룹 권한 자체는 UI 편의 기능으로 보고, 실제 접근 통제는 LiteLLM 팀 단위 모델 목록 제한에 의존하는 이중 방어 구조를 권장.
- **출처**: [open-webui/open-webui Discussion #7689](https://github.com/open-webui/open-webui/discussions/7689) — GitHub 디스커션; [open-webui/open-webui#8002](https://github.com/open-webui/open-webui/issues/8002) — GitHub 이슈

### 오프라인(에어갭) 환경에서 로그인 후 흰 화면(UI 미로드)
- **문제 상황**: 인터넷 차단 환경에서 `HF_HUB_OFFLINE=1`만 설정하고 로그인하면 API 요청은 200 OK인데 화면이 완전히 흰 화면으로 멈춤.
- **원인**: 오프라인 모드에서 외부 리소스 조회가 타임아웃 없이 대기하며 프론트엔드 렌더링이 막히는 것으로 추정.
- **해결/우회**: 공식 오프라인 모드 가이드는 `OFFLINE_MODE=true`, `HF_HUB_OFFLINE=1`과 함께 `RAG_EMBEDDING_MODEL_AUTO_UPDATE=false`, `RAG_RERANKING_MODEL_AUTO_UPDATE=false`, `WHISPER_MODEL_AUTO_UPDATE=false`를 **함께** 켜고, 필요한 임베딩/리랭커/Whisper 모델을 인터넷 환경에서 미리 받아 캐시 디렉토리에 넣어둔 뒤 오프라인 모드를 켜는 순서를 권장. EP04의 반입 목록에 Open WebUI 자체의 내부 임베딩/리랭킹/Whisper 모델은 빠져 있어(RAG는 별도 Qdrant 파이프라인을 쓰지만 Open WebUI 내장 기능을 켤 경우) 확인이 필요.
- **출처**: [open-webui/open-webui#9403](https://github.com/open-webui/open-webui/issues/9403) — GitHub 이슈; [공식 문서 - Offline Mode](https://docs.openwebui.com/tutorials/maintenance/offline-mode/)

### 대화 DB 백업 시 벡터 데이터(RAG 임베딩)가 누락되기 쉬움
- **문제 상황**: 관리자 화면의 "Download Database" 기능은 `webui.db`(사용자/설정/채팅)만 받고, RAG용 `vector_db`는 별도로 챙겨야 한다는 점이 초기엔 잘 알려지지 않아 복원 후 문서 검색 기능이 깨지는 사례가 반복됨.
- **해결/우회**: 데이터 디렉토리(`/app/backend/data`) 전체를 컨테이너를 잠깐 정지한 뒤 백업하는 방식이 커뮤니티 검증 방법. EP11의 감사 로그 보관(6개월)과 별개로, **재해복구 관점의 정기 백업 대상에 대화 DB뿐 아니라 Qdrant(EP15·EP16의 벡터 데이터)까지 포함되는지** 별도로 확인할 것.
- **출처**: [open-webui/open-webui Discussion #8418](https://github.com/open-webui/open-webui/discussions/8418) — GitHub 디스커션; [공식 문서 - Backups](https://docs.openwebui.com/tutorials/maintenance/backups/)

> **관련 편**: [EP11. OpenWebUI 연동 & 사용자 추적](구축기/EP11-OpenWebUI-연동-사용자-추적.md)

## 7. Qdrant + 한국어 RAG

EP15·EP16에서 문장 분리 청킹, BGE-M3 임베딩, 하이브리드 검색(RRF), 출처 인용 프롬프트까지 다뤘습니다. 한국어 규정 문서 RAG 특유의 함정과 Qdrant 운영 이슈를 보완합니다.

### BGE-M3는 다국어 범용 모델이라 한국어 특화 성능이 상대적으로 약함
- **문제 상황**: BAAI 공식 모델 카드에 "중국어·영어 외 언어 학습이 불충분해 추가 학습이 필요"하다고 명시. 한국어 임베딩 벤치마크(금융 도메인)에서 원본 BGE-M3의 Top-1 NDCG는 0.6578에 그침.
- **해결/우회**: 한국어 코퍼스로 파인튜닝한 BGE-m3-ko 계열 모델을 쓰면 같은 벤치마크에서 Top-1 NDCG가 0.7456으로 개선(단 다른 벤치마크에서는 오히려 하락하는 사례도 있어 **자체 사내 QA셋(EP08·EP14가 이미 쓰고 있는 50문항)으로 원본 BGE-M3 대비 실제 개선 여부를 검증한 뒤 교체 여부를 결정**할 것).
- **출처**: [dragonkue/BGE-m3-ko](https://huggingface.co/dragonkue/BGE-m3-ko) — HuggingFace 모델 카드

### BGE-M3 긴 문서(8192 토큰) 임베딩은 청킹 없이 쓰면 품질이 크게 저하
- **문제 상황**: 8192 토큰 전체를 하나의 벡터로 압축하면 세부 정보가 손실돼 특정 조항을 정확히 못 짚어내는 성능 저하 발생(nDCG@10이 16.5까지 하락하는 사례).
- **원인**: 긴 시퀀스를 단일 벡터로 pooling할 때 정보 손실.
- **해결/우회**: BAAI 개발자가 공식 디스커션에서 "512 토큰 정도의 청크가 충분하다"고 권고 — **EP15의 400자 청킹(대략 이 범위)이 이미 이 권고와 일치**하는 선택이었음을 확인해주는 근거 자료.
- **출처**: [HuggingFace BAAI/bge-m3 Discussion #59](https://huggingface.co/BAAI/bge-m3/discussions/59) — 공식 개발자 답변; [M3-Embedding 논문](https://arxiv.org/pdf/2402.03216)

### 표 구조가 많은 규정/약관 PDF는 단순 텍스트 추출로 파싱 실패
- **문제 상황**: 표 제목과 셀 데이터 간 연결이 끊기거나 계층 구조가 손실돼, 숫자는 남아있어도 어느 항목의 값인지 알 수 없게 됨.
- **원인**: 병합된 셀, 비정형 레이아웃을 단순 텍스트 추출 도구가 처리하지 못함. 스캔 PDF는 아예 처리 불가.
- **해결/우회**: 텍스트 기반 표는 Camelot/PDFPlumber, 이미지 기반 표는 OCR 조합. 표를 Markdown/HTML로 변환해 행/열 구조를 보존한 채 저장하는 방식을 권장. **EP15는 문장 분리 기반 청킹만 다뤘는데, 금융 상품 매뉴얼·약관 특성상 표가 포함된 문서가 섞여 있을 가능성이 높아 이 부분이 별도 보강 대상**.
- **출처**: [velog - 표가 많은 복잡한 PDF RAG](https://velog.io/@woodyalmond/%ED%91%9C%EA%B0%80-%EB%A7%8E%EC%9D%80-%EB%B3%B5%EC%9E%A1%ED%95%9C-PDF-RAG-%ED%95%98%EA%B8%B0) — 블로그; [kt cloud 기술블로그](https://tech.ktcloud.com/entry/2025-09-ktcloud-ai-rag-parsing-%EC%A0%84%EC%B2%98%EB%A6%AC-%EC%B5%9C%EC%A0%81%ED%99%94) — 2025-09

### Qdrant 대량 업로드 중 "Optimization error: Out of memory" — 온디스크 설정으로도 완전히 막지 못함
- **문제 상황**: 대규모 벡터 업로드 시 `vectors.on_disk=true`, `hnsw.on_disk=true`를 켰음에도 `Out of memory` 에러 발생.
- **원인**: HNSW 인덱스 최적화(세그먼트 병합) 작업 자체가 온디스크 설정과 무관하게 상당한 RAM을 요구.
- **해결/우회**: 세그먼트 크기·동시 최적화 스레드 수를 낮춰 대응. EP12의 주 1회 문서 반입 파이프라인이 upsert를 자동화하고 있는데, 사내 문서 전체 규모가 커질수록 이 문제와 마주칠 가능성이 있어 컬렉션 크기를 주기적으로 모니터링할 것.
- **출처**: [qdrant/qdrant#2350](https://github.com/qdrant/qdrant/issues/2350) — GitHub 이슈

### Qdrant 대량 upsert 시 컨센서스 실패 및 타임아웃 (분산 클러스터)
- **문제 상황**: 분산 클러스터에서 고처리량 upsert 시 클라이언트 타임아웃, 일부 샤드 중단.
- **원인**: 모든 upsert에 `wait: true`를 걸어 전체 레플리카 동기화를 강제한 상태에서 고처리량 요청이 몰려 합의 오버헤드 누적.
- **해결/우회**: 배치 크기 최적화(공식 문서는 100~500개 단위 배치를 권장), 타임아웃 값 조정. EP12의 `upsert_document` 스크립트는 단건 처리 위주라 대량 갱신 시 배치화를 고려할 것.
- **출처**: [qdrant/qdrant#5642](https://github.com/qdrant/qdrant/issues/5642) — GitHub 이슈; [공식 문서 - Bulk Uploading](https://qdrant.tech/articles/indexing-optimization/)

### 하이브리드 검색(RRF) 도입 시 실측 개선 폭
- **참고 자료**: RRF(k=60이 사실상 표준값)로 dense+sparse를 병합하면 dense-only 대비 NDCG가 26~31% 개선, Recall@1000이 0.87→0.98로 상승한 벤치마크 사례. 하이브리드+리랭킹 조합은 dense-only 대비 Recall@5가 39% 개선. **EP16이 도입한 RRF 방식이 이런 실측 개선 폭과 방향이 일치**함을 뒷받침.
- **출처**: [Atlan - Hybrid RAG](https://atlan.com/know/hybrid-rag/); [tianpan.co - Hybrid Search in Production](https://tianpan.co/blog/2026-04-12-hybrid-search-production-bm25-dense-embeddings) — 2026-04

### BM25 vs SPLADE — sparse 벡터 생성 방식 선택
- **문제 상황**: BM25(전통적 용어빈도 기반)는 어휘 확장이 전혀 없어 쿼리에 없는 단어로 표현된 문서를 못 찾음.
- **원인**: BM25는 순수 용어 빈도 매칭이라 동의어·유사 표현을 놓침. SPLADE(트랜스포머 기반 학습형 sparse)는 어휘 전체로 확장된 표현을 만들어 이를 완화하지만 추론 비용이 증가.
- **해결/우회**: **정확한 식별자·조항 번호 매칭이 중요한 EP16의 "연차" 키워드 검색 같은 경우는 BM25가 오히려 안정적** — 지금 방식이 도메인에 맞는 선택. 의미적 확장이 더 필요해지는 질의 유형이 늘어나면 SPLADE나 Qdrant 자체의 경량 sparse 모델(BM42) 도입을 검토.
- **출처**: [Zilliz - SPLADE vs BM25](https://zilliz.com/learn/comparing-splade-sparse-vectors-with-bm25); [Qdrant 공식 - BM42](https://qdrant.tech/articles/bm42/)

### 금융 도메인 멀티턴 RAG의 환각 벤치마크 — 대화가 길어질수록 오류 누적
- **참고 자료**: 한국 금융 도메인 멀티턴 RAG에서 검색 문서와 모순되는 응답, 수치·정책 정보의 부정확한 표현, 대화가 이어질수록 오류가 누적되는 패턴이 벤치마크로 정량 확인됨.
- **시사점**: **EP16이 이미 적용한 "근거 없으면 모른다고 답하라" + 출처 표시 프롬프트가 이런 누적 오류를 차단하는 데 유효한 접근**이라는 걸 학술적으로 뒷받침. 다만 이 벤치마크가 특히 "멀티턴"에서 오류가 누적된다고 지적하는 만큼, EP16의 사내 QA셋 검증이 단발 질문 위주였다면 **여러 턴 이어지는 대화 시나리오도 검증 항목에 추가**할 것을 권장.
- **출처**: [K-FinHallu 논문 (arXiv)](https://arxiv.org/pdf/2605.29523) — 2026

## 8. 에어갭 반입 절차

EP04·EP06·EP12에서 manifest.json 기반 반입, 체크섬 검증, dnf 로컬 저장소까지 다뤘습니다. 실제 오프라인 dnf 저장소 운영과 대용량 파일 반입에서는 그보다 세부적인 함정들이 보고됩니다.

### createrepo_c 구버전이 RHEL8/9 모듈 메타데이터를 깨뜨려 의존성 충돌
- **문제 상황**: 로컬 저장소에서 `dnf install`을 하면 `cannot install both perl-libs-4:...-404.module... and perl-libs-4:...-416.el8...` 같은 의존성 충돌 에러.
- **원인**: `createrepo_c` 0.16.2-1.el8 이전 버전은 RHEL8/9의 모듈(module) 스트림 메타데이터를 처리하지 못해, 로컬 저장소를 재생성할 때 모듈 정보가 통째로 유실됨.
- **해결/우회**: `reposync`가 받아온 repodata를 그대로 쓰고 `createrepo_c`를 별도로 재실행하지 않거나, 반드시 0.16.2-1.el8 이상 버전 사용. **EP04·EP08의 `createrepo_c ./staging/packages/nvidia` 단계가 정확히 이 위험 지점** — 반입 전후 양쪽에서 `dnf repoclosure`로 의존성이 실제로 풀리는지 검증하는 단계를 추가할 것을 권장.
- **출처**: [Red Hat Knowledgebase - Createrepo module conflict](https://access.redhat.com/solutions/4888921) — 공식문서

### dnf GPG 서명 검증 실패 — 캐시된 옛 키가 남아있는 문제
- **문제 상황**: `repomd.xml GPG signature verification error: Bad GPG signature` 또는 서명 자체가 없다는 에러로 설치가 중단됨.
- **원인**: 저장소가 서명 키를 교체(만료 연장 등)해도 dnf가 저장소별로 캐시해둔 pubring에는 옛 키가 남아 있어 새 메타데이터 서명과 매치되지 않음.
- **해결/우회**: 저장소별 캐시(pubring) 삭제 후 GPG 키 재임포트. **EP06의 manifest.json에 GPG 키 자체를 별도 반입 항목으로 포함시키고, 반입 후 명시적으로 재임포트하는 절차를 추가**하는 걸 권장 — 지금 manifest 예시에는 GPG 키 항목이 없음.
- **출처**: [Red Hat Knowledgebase - GPG 검증 오류](https://access.redhat.com/solutions/7019126)

### FAT32 USB로는 4GB 이상 모델 파일을 애초에 담을 수 없음
- **문제 상황**: 수십GB짜리 safetensors/GGUF 단일 파일을 USB에 복사하려 하면 "파일이 너무 커서 복사할 수 없다"는 오류로 전송 자체가 시작 안 됨.
- **원인**: FAT32는 단일 파일 크기가 4GB를 넘을 수 없는 구조적 제약. 망연계용으로 오래된 규정에 맞춰 FAT32 매체를 지정한 기관에서 자주 발생.
- **해결/우회**: 매체를 exFAT/NTFS로 재포맷(exFAT은 저널링이 없어 정전 시 손상에 더 취약하므로 검역 규정과 상충 여부 확인) 또는 파일을 4GB 미만으로 분할 후 재조립. **EP04의 Qwen2.5-32B(약 64GB), vLLM 이미지(약 12GB)는 이 제약에 직접 걸리는 크기** — 반입 매체 포맷을 사전에 반드시 확인할 것.
- **출처**: [WinXDVD - FAT32 파일 크기 제한](https://www.winxdvd.com/resize-video/fat32-file-size-limit.htm)

### 대용량 파일 전송 중단 시 "존재하지만 손상된" 파일 생성 — 크기 확인만으로는 못 잡음
- **문제 상황**: 전송 중 네트워크가 끊기면 크기 체크 없이 중단 시점까지의 바이트만 저장된 채로 파일이 "존재"하게 되고, 이후 로딩 시점(`invalid magic number`, `unexpected end of file`)에야 손상이 발견됨.
- **해결/우회**: `huggingface-cli`처럼 재개 다운로드를 지원하는 도구 사용. **무엇보다 EP04에서 뽑아둔 sha256 체크섬을 반입 후(EP06 체크리스트) 재계산해 대조하는 절차가 이 문제의 실질적 방어선** — EP06이 이미 이 절차를 포함하고 있어 구조적으로는 안전하지만, "크기만 맞으면 통과"로 절차가 느슨해지지 않도록 체크섬 검증을 생략 불가 항목으로 명문화해둘 것.
- **출처**: [HuggingFace Forums - Interrupted Downloads](https://discuss.huggingface.co/t/solving-interrupted-downloads-of-large-models-on-hugging-face-consistency-check-failure-with-deepseek-v3/155462)

### 망연계 검역 솔루션의 파일 크기 제한이 LLM 모델 규모보다 훨씬 작음
- **문제 상황**: 엔터프라이즈 DLP/위협탐지 게이트웨이의 스캔 가능 파일 크기 상한이 통상 128MB~400MB 수준이라, 수십GB 모델 파일은 스캔이 스킵되거나(Fallback: Allow) 차단됨.
- **원인**: DLP/CASB 제품이 애초에 문서·오피스 파일을 전제로 설계돼 대용량 파일 스캔을 지원하지 않음.
- **해결/우회**: 대용량 모델 파일이 게이트웨이를 "통과"했다고 해서 "백신 검사를 통과했다"는 뜻이 아닐 수 있음을 인지하고, **EP06 체크리스트의 "전 파일 백신 검사 완료"를 별도의 오프라인 전용 스캔 PC에서 재확인**하는 절차로 구체화할 것 — 게이트웨이 통과만으로는 검증이 안 될 수 있음.
- **출처**: [Netskope 공식 문서 - Advanced File Scanning](https://docs.netskope.com/en/advanced-file-scanning)

### docker save/load의 대안 — skopeo sync·프라이빗 레지스트리 미러링
- **문제 상황**: `docker save`/`load`(EP04·EP07 방식)는 이미지 1개씩 수동으로 저장·전송·로드해야 해, 이미지 수가 늘어날수록 반입 패키지 크기와 작업량이 선형으로 증가.
- **해결/우회**: `skopeo sync`는 데몬 없이 소스 레지스트리 전체(또는 태그 필터링된 이미지 셋)를 한 번에 로컬 디렉터리나 대상 레지스트리로 복사 가능, YAML 설정으로 여러 이미지 일괄 관리. **EP12에서 이미 내부 프라이빗 레지스트리(`podman run ... localhost/registry:2`)를 도입했으므로, 다음 분기 반입부터는 `docker save`/`load` 대신 `skopeo sync`로 반입 자체를 자동화하는 걸 검토**할 만함. 반입 후 배포는 Harbor(취약점 스캔·서명 검증·RBAC 포함) 같은 표준 레지스트리로 넘어가는 게 국방/공공 에어갭 환경의 사실상 표준.
- **출처**: [skopeo-sync 공식 문서](https://github.com/containers/skopeo/blob/main/docs/skopeo-sync.1.md); [Red Hat Developer - Skopeo](https://developers.redhat.com/articles/2025/09/24/skopeo-unsung-hero-linux-container-tools)

### NVIDIA 드라이버가 커널 버전 불일치로 DKMS 빌드 실패
- **문제 상황**: `Error! Bad return status for module build on kernel: ...`, 빌드 로그에 `fatal error: nv-misc.h: No such file or directory`.
- **원인**: 반입한 드라이버 배포판이 대상 서버의 실제 커널과 호환되지 않아 DKMS가 필요한 헤더를 찾지 못함. 폐쇄망에서는 커널 업데이트와 드라이버 반입 시점이 어긋나기 쉬워 특히 자주 발생.
- **해결/우회**: 반입 manifest에 "검증된 커널 버전 목록"을 명시하고, 반입 전 폐쇄망과 동일한 커널 버전의 테스트 서버에서 DKMS 빌드를 먼저 검증. **EP08은 드라이버 설치 후 바로 재부팅·검증하는 절차였는데, 만약 EP12 이후 서버가 보안 패치로 커널이 업데이트된 시점에 드라이버를 재반입하면 이 문제와 마주칠 수 있음** — 커널 버전과 드라이버 버전의 조합을 반입 manifest에 명시적으로 기록해둘 것.
- **출처**: [Proxmox 포럼 - NVIDIA 드라이버 빌드 실패](https://forum.proxmox.com/threads/cant-install-nvidia-driver-error-bad-return-status-for-module-build-on-kernel-5-15-74-1-pve-x86_64.118321/) — 포럼(실제 로그 포함)

### Secure Boot 환경에서는 DKMS가 커널 모듈을 자동 서명하지 못함
- **문제 상황**: Secure Boot가 켜진 서버에서 드라이버 설치 후 재부팅하면 `nvidia`, `nvidia_drm`, `nvidia_uvm` 모듈이 로드되지 않음.
- **원인**: Secure Boot는 신뢰된 키(MOK)로 서명된 모듈만 로드하는데, DKMS는 커널 업데이트 시 재빌드는 자동화해도 서명은 자동화하지 않음 — MOK 생성·서명은 수동 개입이 필요.
- **해결/우회**: MOK 키 쌍을 생성해 `mokutil --import`로 등록(재부팅 시 암호 입력으로 확정) 후 DKMS `post_build` 훅에 서명 스크립트 연결. 금융권 서버가 Secure Boot를 쓴다면 EP08의 드라이버 설치 절차에 이 단계가 빠져 있을 가능성 — 반입 전 대상 서버의 Secure Boot 활성화 여부를 확인할 것.
- **출처**: [if-not-true-then-false.com - Secure Boot NVIDIA 서명](https://www.if-not-true-then-false.com/2025/debian-nvidia-guide/3/)

### 국내 금융권 망분리 규제 완화 동향 — 2026년 시행세칙 개정
- **참고 자료**: 2013년 전산대란 이후 강도 높게 유지되던 금융권 망분리 규제가 2026년 4월 20일 전자금융감독규정 시행세칙 개정으로 일부 완화됨. 금융보안원 평가를 통과한 SaaS에 한해 내부 업무망 사용을 허용하되, 신청 자격을 총자산 10조원 이상·전담 CISO를 둔 금융사로 제한. 1차 선정에 보험·카드업권이 포함됨.

### 국가 망 보안체계(N2SF) — 등급별 차등 통제로의 전환 (공공기관 참고)
- **참고 자료**: 기존 "일괄 물리적 망분리" 대신 정보 자산을 기밀(C)·민감(S)·공개(O) 3등급으로 분류해 등급별 보안통제를 차등 적용하는 N2SF로 정책 전환 중. 준비→등급분류→위협식별→보안대책수립→적절성평가의 5단계.
- **시사점**: 금융권이 아닌 공공기관 버전으로 이 구축기를 응용한다면, 반입 대상 데이터·모델의 민감도를 먼저 등급 분류한 뒤 그에 맞는 통제 수준(물리적 완전 분리 vs 논리적 분리)을 적용받는 근거로 활용 가능 — EP02의 "폐쇄망 안의 어떤 장비도 스스로 인터넷에 나가면 안 된다"는 일괄 원칙보다 세분화된 접근.
- **출처**: [디딤 - 국가 망 보안체계(N2SF)](https://didim.com/blog/n2sf_details) — 기술 블로그

1. **배포 전 체크리스트로**: 각 섹션의 사례들을 실제 배포 전 리허설 단계에서 하나씩 재현해보고, 우리 환경(버전·커널·네트워크 구성)에서도 발생하는지 확인하세요.
