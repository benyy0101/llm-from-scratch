# 폐쇄망 멀티에이전트 구축기 (구축기 v2.0)

[구축기(1편)](../구축기-v1.0/README.md)가 "V100 3장으로 RAG + 코딩 어시스턴트 하나를 세우는" 단일 노드 시나리오였다면, 이 시리즈는 그 다음 단계 — **GPU 노드가 여러 대로 늘어났을 때, 서브에이전트 병렬 처리와 멀티봇 협업(오케스트레이션)을 폐쇄망 안에서 어떻게 설계·운영하는가**를 다룹니다. [06-에이전트-오케스트레이션-분석.md](../06-에이전트-오케스트레이션-분석.md)에서 정리한 원리(라우팅 이중화 문제, GPU 용량과 오케스트레이션 전략의 관계)를 실제 구축 절차로 옮긴 것이 이 시리즈입니다.

## 가상 시나리오

1편과는 다른 조직·설정입니다. 다만 "새 장비를 사는 대신 유휴 자산을 재활용한다"는 문제의식은 이어갑니다.

| 항목 | 내용 |
|---|---|
| 기관 | **H전자 AI혁신센터** (가상 — 실명 아님) |
| 목표 | 연구소·법무팀·품질관리팀이 함께 쓰는 멀티에이전트 플랫폼 — 문헌·특허 병렬 조사, 부서별 전담 봇(리서처·법무검토·품질분석), 개발팀 코딩 어시스턴트 |
| 네트워크 | 완전 물리적 망분리(에어갭) — 대기업 기술유출 방지 정책 |
| 장비 | 컴퓨터비전 R&D 과제 종료 후 유휴 상태이던 **DGX H100 4대**, 노드 간 InfiniBand 결합 없이 **독립 랙 4곳에 분산 배치**(클러스터링 없음) |
| LLM | 노드별 역할 분리 — 추론용(Qwen2.5-72B), 코드용(Qwen2.5-Coder-32B), 임베딩용(BGE-M3), 예비/페일오버 |
| 오케스트레이션 | Hermes Agent(Bot Mode, 서브에이전트 위임) + LiteLLM Router(least-busy 라우팅) — 비즈니스 봇 3개(리서처·법무검토·품질분석)만 대상, 개발팀은 Hermes 미경유 |
| 스택 | Podman · vLLM · LiteLLM · Qdrant · Hermes Agent · Open WebUI · Continue.dev · Cline |

1편의 "V100 3장, RAG 하나"보다 규모가 커진 만큼, 이번 시리즈의 실제 문제의식은 **"노드가 여러 대일 때 라우팅·동시성·역할 분리를 어떻게 잘못 설계하면 오히려 손해를 보는가"**입니다 — 노드를 늘렸다고 자동으로 오케스트레이션이 좋아지는 게 아니라는 걸 계속 확인하게 됩니다.

## 1편과의 관계

1편([구축기-v1.0/README.md](../구축기-v1.0/README.md))의 서빙 스택(vLLM·LiteLLM·Podman)을 그대로 전제로 깔고, 그 위에 오케스트레이션 레이어(서브에이전트 위임, 모델 라우팅, 멀티봇)를 얹는 구성입니다. vLLM 배포나 Podman 운영처럼 1편에서 이미 다룬 절차는 여기서 반복하지 않고 1편 문서를 그대로 참조합니다 — 이 시리즈가 새로 다루는 건 **"노드가 여러 대, 클라이언트가 여러 개일 때"** 생기는 문제들입니다.
