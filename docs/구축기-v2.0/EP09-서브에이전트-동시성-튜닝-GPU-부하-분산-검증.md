# EP09. 서브에이전트 동시성 튜닝 & GPU 부하 분산 검증

> 시리즈: [폐쇄망 멀티에이전트 구축기](README.md) · 이전: [EP08. Hermes Agent 설치 & Bot Mode 구성](EP08-Hermes-Agent-설치-Bot-Mode-구성.md) · 다음: [EP10. 봇별 역할 분리 운영](EP10-봇별-역할-분리-운영.md)

Phase 4(실전 운영) 첫 편이에요. [EP02](EP02-전체-아키텍처-설계.md)에서 추정만 해뒀던 "GPU 기준 최대 100건 동시 요청", 이번 편에서 실제로 재현해봤습니다. 결과부터 말하면 — **1차 테스트는 목표치를 못 지켰고**, 원인을 찾아 구성을 하나 바꾼 뒤에야 통과했어요.

## 🧪 1차 테스트 — 부서 3곳이 동시에 피크를 치는 최악의 경우

[EP02](EP02-전체-아키텍처-설계.md)에서 서브에이전트를 쓰는 부서(연구소·법무팀·품질관리팀)가 동시에 피크 시간대를 맞는다고 가정하고, 각자 최대치(부서당 서브에이전트 4개)로 요청을 쐈습니다.

| 부서 | 피크 동시 접속 | 서브에이전트 배수 | GPU에 꽂히는 요청 |
|---|---|---|---|
| 연구소 | 10명 | ×4 | 40건 |
| 법무팀 | 7명 | ×4 | 28건 |
| 품질관리팀 | 7명 | ×4 | 28건 |
| **합계** | | | **96건** |

이 96건이 전부 `infer-primary`(노드1, 상한 24) 하나로 몰려요. [EP07](EP07-LiteLLM-Router-least-busy-라우팅-구성.md)에서 만든 노드4 페일오버는 "장애 시"에만 쓰기로 했으니 이번 테스트에선 꺼둔 채로 돌렸습니다.

```
[load-test] concurrency=96, target=infer-primary
[result] p50 first-token: 2.1s | p95 first-token: 11.4s | timeout_rate: 6.3%
```

p95가 11.4초 — [EP02](EP02-전체-아키텍처-설계.md)에서 잡은 목표(3초)를 크게 넘겼고, 타임아웃도 6.3% 발생했어요. [06-에이전트-오케스트레이션-분석.md 5절](../06-에이전트-오케스트레이션-분석.md)에서 경고했던 "GPU 여유 없이 서브에이전트를 늘리면 큐 대기시간만 커진다"가 정확히 재현된 거예요 — 다만 저희는 GPU 1~3장이 아니라 노드 하나에 GPU 4장(H100)을 쓰고 있었는데도 이 문제가 났습니다.

## 🔍 원인 — 노드는 안 바쁜데 "등록된 슬롯"이 모자랐어요

`nvidia-smi`로 확인해보니 노드1의 GPU 사용률은 60% 안팎, VRAM도 여유가 있었어요. 문제는 GPU 자체가 아니라 [EP04](EP04-LiteLLM-Router-다중노드-라우팅-설계.md)에서 잡은 `max_parallel_requests: 24`라는 **게이트웨이 쪽 상한**이었습니다. vLLM의 continuous batching은 사실 24보다 훨씬 많은 요청을 동시에 받아도 되는데, 게이트웨이가 미리 낮게 잡아둔 상한 때문에 나머지가 전부 대기열에 쌓인 거예요.

그럼 상한을 그냥 올리면 되지 않냐 싶었는데, [EP03](EP03-DGX-노드-선정과-독립형-vs-클러스터형-판단.md)에서 노드1은 GPU 4장만 쓰고 나머지 4장은 "배치 여유"로 비워뒀던 게 기억났어요. 이 여유분을 실제로 활용하지 않고 상한만 숫자로 올리면, 진짜 물리적 한계에 부딪힐 뿐이었습니다.

## 🧩 해결 — 노드1 안에 레플리카를 하나 더 얹었어요

노드4를 상시 가동으로 돌리는 방법도 있었는데, 그건 [EP03](EP03-DGX-노드-선정과-독립형-vs-클러스터형-판단.md)에서 정한 "노드4는 순수 예비"라는 원칙을 깨는 거라 최후의 수단으로 남겨뒀어요. 대신 **노드1 안에서 놀고 있던 GPU 4장으로 vLLM 레플리카를 하나 더 띄우는** 쪽을 먼저 시도했습니다.

```bash
# 노드1의 남은 GPU 4장으로 두 번째 인스턴스 기동
podman run -d --name vllm-infer-2 \
  --device nvidia.com/gpu=4,5,6,7 \
  --network airgap-net \
  -v /shared/models/qwen2.5-72b-instruct:/models/infer:Z \
  -p 8001:8000 \
  localhost/vllm-h100:latest \
  vllm serve /models/infer --tensor-parallel-size 4 --max-num-seqs 24
```

그리고 [EP04](EP04-LiteLLM-Router-다중노드-라우팅-설계.md)에서 만든 `model_list`에 이 레플리카를 그냥 배포 하나 더 등록하는 것으로 끝났어요.

```yaml
  - model_name: infer-primary
    litellm_params:
      model: openai/Qwen2.5-72B-Instruct
      api_base: http://node1-infer-2:8001/v1     # 같은 노드, 두 번째 인스턴스
      max_parallel_requests: 24
```

여기서 [EP02](EP02-전체-아키텍처-설계.md)에서 짰던 설계가 진짜 도움이 됐어요 — `model_name`을 논리적 이름으로 두고 그 뒤에 배포를 여러 개 매다는 구조라, **아키텍처를 다시 그릴 필요 없이 config에 항목 하나 추가하는 것만으로 용량이 늘어났습니다.** 노드4는 여전히 완전히 꺼진 상태로, 원래 역할(장애 시 예비) 그대로 남았고요.

## ✅ 재테스트 결과

```
[load-test] concurrency=96, target=infer-primary
[result] p50 first-token: 1.6s | p95 first-token: 2.7s | timeout_rate: 0%
```

레플리카 하나 추가로 실질 상한이 24 → 48로 늘어나면서 p95가 2.7초로 목표(3초) 안에 들어왔습니다. 96건 중 최대 48건까지는 노드1이 바로 처리하고, 나머지는 짧게 대기했다가 처리되는 정도였어요.

## 📋 이번 편에서 확정한 것

| 항목 | 결정 |
|---|---|
| 1차 테스트 결과 | 96건 동시 요청 시 p95 11.4초, 타임아웃 6.3% — 목표 미달 |
| 원인 | GPU 자체가 아니라 게이트웨이 `max_parallel_requests` 상한 부족 |
| 해결 | 노드1의 유휴 GPU 4장으로 레플리카 추가, `model_list`에 배포 항목만 추가 |
| 재테스트 결과 | p95 2.7초, 타임아웃 0% — 목표 충족 |
| 노드4 원칙 | 그대로 유지(순수 예비), 용량 문제는 노드 내부 레플리카로 해결 |
| 부서당 서브에이전트 상한 | 4개 유지(EP01·EP02 결정 그대로) |

다음 편에서는 부서별로 봇을 실제로 운영하면서, 가상 키별 사용량과 봇별 응답 품질을 어떻게 모니터링하는지 다룹니다.

---

📌 **EP.09 한 줄 요약**
서브에이전트를 포함한 최악의 동시 요청(96건)을 재현했더니 GPU가 아니라 게이트웨이 상한 때문에 목표를 못 지켰고, 노드1의 유휴 GPU로 레플리카를 하나 추가해 `model_list`에 배포 항목만 더하는 것으로 노드4의 예비 역할을 건드리지 않고 문제를 해결했다.
