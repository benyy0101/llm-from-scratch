# EP11. 모니터링 & 노드 페일오버

> 시리즈: [폐쇄망 멀티에이전트 구축기](README.md) · 이전: [EP10. 봇별 역할 분리 운영](EP10-봇별-역할-분리-운영.md) · 다음: [EP12. 멀티봇 협업 워크플로우 실전 사례](EP12-멀티봇-협업-워크플로우-실전-사례.md)

[1편 EP13](../구축기-v1.0/EP13-모니터링-트러블슈팅.md)에서 "계층마다 다른 지표를 보고, 알람도 계층별로 다르게 건다"는 원칙을 세웠었죠. [EP02](EP02-전체-아키텍처-설계.md)에서 계층을 하나 더(오케스트레이션) 늘렸으니, 이번 편에서는 그 새 계층에 뭘 붙여야 하는지 정하고, 그동안 설계만 해뒀던 노드4 페일오버를 실제 장애 훈련으로 검증합니다.

## 📊 계층별 지표, 오케스트레이션 계층만 새로 추가했어요

| 계층 | 주요 지표 | 어디서 나오나 |
|---|---|---|
| 서빙 계층 (vLLM, 노드1~4) | GPU 사용률, `vllm:gpu_cache_usage_perc`(노드별), `time_to_first_token` | vLLM `/metrics` × 4노드 |
| 게이트웨이 계층 (LiteLLM) | 배포별(deployment) 요청 수·실패율, 헬스체크 상태 | LiteLLM `/metrics` |
| **오케스트레이션 계층 (Hermes Agent, 신규)** | **봇별 서브에이전트 동시 스폰 수, 위임 실패율, 봇별 응답 지연** | Hermes Agent `/metrics` |
| 접근 계층 (Open WebUI/Continue.dev) | 동시 접속자 수, 세션 오류 | 1편과 동일 |

1편에는 없던 계층이라 지표부터 새로 정의해야 했는데, 제일 중요하게 본 건 **"봇별 서브에이전트 동시 스폰 수"**였어요. [EP09](EP09-서브에이전트-동시성-튜닝-GPU-부하-분산-검증.md)에서 확인했듯 이 숫자가 튀는 순간 게이트웨이·서빙 계층까지 연쇄로 영향을 받으니, 문제가 어디서 시작됐는지 가장 먼저 가리켜주는 지표가 됩니다.

```yaml
# prometheus.yml에 추가한 부분
scrape_configs:
  - job_name: hermes-agent
    static_configs:
      - targets: ["hermes-agent:7000"]
  - job_name: vllm-nodes
    static_configs:
      - targets: ["node1-infer:8000", "node1-infer-2:8001", "node2-code:8000", "node3-embed:8000"]
```

## 🔔 알람 — "누구한테 갈지"를 계층별로 다시 정했어요

| 계층 | 알람 조건 | 수신자 |
|---|---|---|
| 오케스트레이션 | 특정 봇의 동시 서브에이전트 스폰 수가 5분간 상한(4개)에 계속 붙어있음 | 해당 부서 담당자 + 인프라팀 |
| 게이트웨이 | 특정 배포(deployment)의 헬스체크가 2회 연속 실패 | 인프라팀 즉시 알람 |
| 서빙 | 노드별 `gpu_cache_usage_perc > 90%`가 5분 이상 | 인프라팀 |
| 접근 | 1편과 동일 | 보안팀 |

게이트웨이 계층 알람("헬스체크 2회 연속 실패")이 사실상 이번 편의 핵심이에요 — 이게 노드4 페일오버를 수동에서 반자동으로 바꾸는 트리거가 됐습니다.

## 🔥 실제 장애 훈련 — 노드1을 일부러 죽여봤어요

[EP07](EP07-LiteLLM-Router-least-busy-라우팅-구성.md)에서 "장애 감지 → 노드4 자동 기동까지는 수동"이라고 남겨둔 숙제, 이번 편에서 실제 훈련으로 매듭지었습니다. 새벽 시간대에 노드1 컨테이너를 강제로 내려서 실제 장애를 흉내 냈어요.

```
02:00:00  podman stop vllm-infer vllm-infer-2   (훈련 시작, 노드1 다운)
02:00:34  [health_check] infer-primary/node1-infer: unhealthy (2회 연속)
02:00:34  [alert] 게이트웨이 알람 발송 → 인프라팀
02:03:10  담당자 확인 후 노드4 기동 스크립트 실행
02:03:52  [health_check] infer-primary/node4-standby: healthy
02:03:52  [router] infer-primary 요청 100% → node4-standby로 전환
```

감지까지 34초, 사람이 알람을 보고 판단해서 노드4를 기동하기까지 약 3분 18초가 걸렸어요. 전체 MTTR(장애 인지~복구)은 약 4분. [EP02](EP02-전체-아키텍처-설계.md)에서 잡은 응답 지연 목표를 생각하면 4분은 짧은 시간이 아니라서, 이 훈련 이후로 "담당자 확인" 단계를 없애고 **헬스체크 2회 연속 실패 시 노드4를 자동 기동하는 스크립트**를 게이트웨이 알람에 바로 연결했습니다.

```bash
#!/bin/bash
# node4-auto-failover.sh — 게이트웨이 알람 webhook에서 직접 호출
podman start vllm-infer-standby
# 기동 후 헬스체크 통과까지 대기, 통과하면 슬랙으로 완료 알림만 발송
```

자동화 후 재훈련에서는 감지~복구까지 총 58초로 줄었어요. 다만 "사람 확인 없이 자동으로 예비 자원이 켜진다"는 게 부담스러워서, 자동 기동 이후엔 **반드시 사후 원인 분석 티켓이 자동 생성**되도록 해서 완전히 무인화하지는 않았습니다.

## 📋 이번 편에서 확정한 것

| 항목 | 결정 |
|---|---|
| 오케스트레이션 계층 지표 | 봇별 서브에이전트 동시 스폰 수, 위임 실패율 |
| 신규 알람 | 게이트웨이 헬스체크 2회 연속 실패 시 즉시 알람 |
| 페일오버 방식 | 수동 확인 → 자동 스크립트 기동으로 전환 (MTTR 4분 → 58초) |
| 안전장치 | 자동 기동 후 사후 원인 분석 티켓 자동 생성 (완전 무인화는 지양) |

다음 편에서는 지금까지 부서별로 따로 써온 봇들이 실제로 서로 협업하는 사례 — 예를 들어 리서처 봇이 조사한 내용을 법무검토 봇이 이어받아 검토하는 워크플로우를 다뤄봅니다.
