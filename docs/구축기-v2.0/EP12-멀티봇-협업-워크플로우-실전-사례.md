# EP12. 멀티봇 협업 워크플로우 실전 사례

> 시리즈: [폐쇄망 멀티에이전트 구축기](README.md) · 이전: [EP11. 모니터링 & 노드 페일오버](EP11-모니터링-노드-페일오버.md) · 다음: [EP13. 시리즈 총정리 & 운영 회고](EP13-시리즈-총정리-운영-회고.md)

지금까지는 비즈니스 봇 3개(리서처·법무검토·품질분석)가 각자 부서 안에서만 일했어요. (개발팀은 애초에 Hermes를 거치지 않으니 이번 편 논의에서도 빠집니다.) 이번 편은 [06-에이전트-오케스트레이션-분석.md 3절](../06-에이전트-오케스트레이션-분석.md)에서 소개했던 Hermes Agent의 또 다른 기능 — **봇끼리 서로 메시지를 주고받는 그룹 채팅**을 실제로 써본 사례입니다. 실제로 부서 경계를 넘는 요청이 들어오고 나서야 이 기능이 왜 필요한지 체감했어요.

## 🧩 계기 — "이거 법무팀한테도 물어봐야 하는 거 아니에요?"

품질관리팀이 불량 원인 조사를 하다가, 원인 후보 중 하나가 "협력사 납품 계약서에 명시된 품질 기준 미달"로 좁혀졌어요. 품질분석 봇이 원인 후보까지는 잘 짚었는데, "이게 계약 위반인지"는 품질분석 봇의 역할 밖이었죠. 이전까지는 사람이 그 결과를 복사해서 법무검토 봇에게 다시 물어보는 식이었는데, 이 과정에서 맥락이 자꾸 누락됐어요.

## 💬 그룹 채팅으로 봇 둘을 직접 붙였어요

```yaml
# /opt/hermes/bots/groups/quality-legal-review.yaml
group:
  name: quality-legal-review
  members: [quality, legal]
  max_rounds: 3            # Hermes Agent 기본값 — 무한 핑퐁 방지
  trigger: manual          # 사람이 그룹 채팅을 시작해야 함(자동 트리거 아님)
```

```
[사람] @quality 이번 불량 리포트(QR-2026-0142) 원인 후보 정리해줘. 계약 관련 항목이 있으면 @legal 불러줘.

[품질분석 봇] 원인 후보 3개 중 2번(협력사 원자재 품질 기준 미달)이 유력. 계약서 조항 확인 필요해 보임 → @legal

[법무검토 봇] 계약서 제12조(품질 기준) 확인 결과, 협력사가 계약상 명시된 허용 불량률(0.3%)을 초과. 위약금 조항(제18조) 검토 대상. 근거 조항 인용 완료.

[품질분석 봇] @legal 확인 감사합니다. 최종 리포트에 "계약 위반 소지 있음, 법무팀 후속 검토 필요"로 반영.
```

3라운드 안에서 대화가 자연스럽게 마무리됐어요. 사람이 중간에서 복사·붙여넣기를 안 해도 됐다는 게 가장 크게 체감한 차이였고, 무엇보다 [EP10](EP10-봇별-역할-분리-운영.md)에서 정한 각 봇의 가드레일(근거 조항 인용, 확신도 표기)이 봇 간 대화에서도 그대로 지켜졌다는 게 인상적이었어요.

## ⚠️ `max_rounds: 3`으로 제한한 이유

처음엔 라운드 제한 없이 테스트해봤는데, 봇 둘이 서로에게 계속 확인 질문을 주고받으면서 답이 없는 대화가 길어지는 경우가 있었어요.

```
[품질분석 봇] @legal 이 조항 해석이 맞는지 한 번 더 확인해줄 수 있어?
[법무검토 봇] @quality 어떤 부분이 불확실한지 구체적으로 짚어줄 수 있어?
[품질분석 봇] @legal 음, 그냥 전반적으로 다시 한번 봐줘
... (이후 핑퐁 반복)
```

이런 패턴이 나오면 토큰만 계속 쓰고 결론이 안 나요. `max_rounds: 3`으로 강제 종료하게 해두고, 3라운드 안에 결론이 안 나면 **"사람 개입 필요"로 자동 에스컬레이션**하도록 정했습니다. [06-에이전트-오케스트레이션-분석.md 6절 체크리스트](../06-에이전트-오케스트레이션-분석.md)의 "봇/서브에이전트가 실패했을 때 대상이 명확한가"를 여기서도 똑같이 적용한 셈이에요 — 그룹 채팅의 실패란 결론 없이 라운드가 끝나는 것이었고, 그 실패의 다음 단계(사람에게 넘기기)를 명확히 정해뒀습니다.

## 📊 도입 이후 한 달 운영 결과

| 항목 | 수치 |
|---|---|
| 그룹 채팅 트리거 횟수 | 월 34건 (품질-법무 22건, 리서치-법무 12건) |
| 평균 라운드 수 | 1.8라운드 (3라운드 도달은 6건, 전부 사람에게 에스컬레이션) |
| 사람 개입 없이 종결된 비율 | 82% |
| 추가 GPU 부하 | 무시할 수준 (봇 간 대화도 동일하게 `infer-primary` 상한 안에서 처리됨) |

GPU 부하가 따로 안 튄 이유는 간단해요 — 그룹 채팅도 결국 [EP04](EP04-LiteLLM-Router-다중노드-라우팅-설계.md)에서 설계한 게이트웨이를 그대로 통과하는 요청일 뿐이라, 새 레이어를 또 만든 게 아니라 **오케스트레이션 계층 안에서 봇 간 상호작용 패턴 하나를 추가한 것**뿐이었거든요.

| 항목 | 결정 |
|---|---|
| 그룹 채팅 대상 | 품질분석 ↔ 법무검토 (상시), 리서처 ↔ 법무검토 (필요 시) |
| 트리거 방식 | 수동(사람이 `@봇이름`으로 그룹 채팅 시작) — 자동 트리거는 도입하지 않음 |
| 라운드 상한 | 3라운드, 초과 시 사람에게 자동 에스컬레이션 |
