# EP01. 왜 멀티에이전트 오케스트레이션인가

> 시리즈: [폐쇄망 멀티에이전트 구축기](README.md) · 다음: [EP02. 전체 아키텍처 설계](EP02-전체-아키텍처-설계.md)

저희 팀(H전자 AI혁신센터)이 이 프로젝트를 시작한 건 컴퓨터비전 R&D 과제가 끝나면서 **DGX H100 4대가 유휴 장비로 빠진 것**을 알게 된 게 계기였어요. 새 예산 승인 없이 이미 자산으로 잡혀있는 장비를 재활용하는 거라 품의는 오히려 쉬웠는데, "그럼 이 4대로 뭘 할까"가 진짜 고민이었습니다.

## 🤔 처음엔 그냥 1편을 복붙하려고 했어요

가장 쉬운 선택지는 [1편(구축기)](../구축기-v1.0/README.md)에서 이미 검증한 걸 그대로 4대에 반복하는 거였어요. vLLM 4벌 띄우고, 부서마다 하나씩 나눠주면 끝 아닌가 — 라고 처음엔 생각했습니다.

그런데 실제 요구사항을 모아보니 이야기가 달랐어요.

| 부서 | 요청 내용 |
|---|---|
| 연구소 | 특허·논문 100건을 한 번에 넣고 각각 요약 + 우리 특허와 겹치는지 교차검증 |
| 법무팀 | 계약서 초안이 들어오면 조항별로 나눠 여러 관점(공정거래·개인정보·라이선스)에서 동시에 검토 |
| 품질관리팀 | 불량 이슈 리포트가 들어오면 원인 후보 3~4개를 각각 파고들어 병렬로 조사한 뒤 종합 |
| 개발팀 | (1편과 동일) 코드 자동완성·리뷰 — Cline/Continue.dev, Hermes 미경유 |

앞의 세 부서 요청이 공통적으로 "**하나의 큰 작업을 여러 개의 독립된 하위 작업으로 쪼개서 동시에 처리하고, 결과를 합쳐달라**"는 패턴이었어요. 이게 바로 [06-에이전트-오케스트레이션-분석.md](../06-에이전트-오케스트레이션-분석.md)에서 정리한 **서브에이전트 위임** 패턴이더라구요. 1편의 "질문 하나에 답변 하나"짜리 구조로는 이 요청들을 감당할 수가 없었습니다.

## 📉 왜 GPU 1~3장 시절엔 이걸 안 했나

사실 1편(V100 3장) 때도 서브에이전트라는 개념 자체는 알고 있었어요. 근데 그때는 일부러 안 썼습니다. 이유는 단순해요 — [06-에이전트-오케스트레이션-분석.md 5절](../06-에이전트-오케스트레이션-분석.md)에 정리했듯, **GPU 여유가 없는 상태에서 서브에이전트를 병렬로 띄우면 처리량이 느는 게 아니라 큐 대기시간만 늘어납니다.** V100 3장으로 이미 현업 40명 + 개발팀 25명을 받고 있었는데, 거기다 "질문 하나당 서브에이전트 3~4개"까지 얹으면 동시 요청 수만 몇 배로 뛰고 개별 응답은 오히려 느려지는 결과가 뻔히 보였거든요.

DGX H100 4대는 상황이 다릅니다. H100 한 장의 연산력·메모리 대역폭이 V100과 세대 차이가 나는 데다(Part 7 하드웨어표 참고), 노드 자체가 4대라 "부서 하나가 서브에이전트를 왕창 스폰해도 다른 노드가 받아줄 여유"가 생겨요. 오케스트레이션을 도입할지 말지는 결국 **"지금 인프라가 그 오케스트레이션이 만들어내는 동시 요청 증가분을 흡수할 여유가 있는가"**로 판단해야 한다는 걸 이번에 명확히 정리했습니다.

## 🧭 그래서 뭘 도입하기로 했나

세 가지를 결합하기로 했어요.

1. **Hermes Agent의 서브에이전트 위임** — 부서별 요청(특허 교차검증, 계약서 다관점 검토, 불량 원인 병렬 조사)을 실제로 여러 하위 에이전트로 쪼개 동시 실행
2. **Hermes Agent Bot Mode** — 연구소·법무팀·품질관리팀마다 전담 봇(리서처·법무검토·품질분석)을 만들어 각자 역할·모델을 고정
3. **LiteLLM Router 다중 노드 라우팅** — 이 모든 봇·서브에이전트의 요청이 4개 노드 중 어디로 갈지는 게이트웨이가 알아서 분산(least-busy)

개발팀만 예외로 뒀어요. 코드 작업은 애초에 VS Code 확장(Continue.dev·Cline)으로 이미 자율적으로 잘 돌아가고 있었고, Hermes Agent에 굳이 "코더 봇"으로 한 번 더 감쌀 이유가 없었습니다. 오히려 반입 심사 대상(EP05)만 하나 더 늘리는 셈이라, **개발팀은 처음부터 Hermes Bot Mode 밖에 두고 LiteLLM 게이트웨이에 직접 연결**하기로 했어요 — 이 판단은 EP08에서 자세히 다룹니다.

핵심 원칙 하나는 이번 시리즈 내내 반복해서 나올 텐데, 미리 못박아둘게요 — **"모델 이름 → 실제 GPU 노드" 라우팅 판단은 LiteLLM 게이트웨이 한 곳에만 두고, Hermes Agent 쪽은 그 게이트웨이 하나만 프로바이더로 바라본다.** Hermes가 자체적으로도 프로바이더 라우팅 기능(`runtime_provider.py`)을 갖고 있다는 걸 알고 나서, 이 둘을 같이 켜두면 라우팅 판단이 두 군데서 따로 놀 수 있다는 걸 깨달았거든요 — 이 문제는 EP04에서 자세히 다룹니다.

|---|---|
| 오케스트레이션 도입 여부 | 도입 — 단, GPU 노드 4대(독립형) 여유가 전제 조건 |
| 서브에이전트 병렬 스폰 상한 | 부서당 최대 4개 동시 (다음 편에서 숫자로 재검증 예정) |
| 라우팅 책임 | LiteLLM 게이트웨이로 단일화, Hermes 자체 라우팅은 비활성화 |
| 봇 구성 | Hermes Bot Mode: 리서처·법무검토·품질분석 3개 봇 / 개발팀: Cline·Continue.dev로 게이트웨이 직결(Hermes 미경유) |
