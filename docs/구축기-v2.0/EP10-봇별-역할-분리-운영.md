# EP10. 봇별 역할 분리 운영 (리서처·법무검토·품질분석)

> 시리즈: [폐쇄망 멀티에이전트 구축기](README.md) · 이전: [EP09. 서브에이전트 동시성 튜닝 & GPU 부하 분산 검증](EP09-서브에이전트-동시성-튜닝-GPU-부하-분산-검증.md) · 다음: [EP11. 모니터링 & 노드 페일오버](EP11-모니터링-노드-페일오버.md)

비즈니스 봇 3개를 띄우고 용량도 맞춰뒀으니 이제 실제로 운영하면서 부딪힌 문제들을 정리할 차례예요. 이번 편은 새 기능을 붙이는 얘기가 아니라, **[EP08](EP08-Hermes-Agent-설치-Bot-Mode-구성.md)에서 정한 봇별 권한 설계가 실제 업무에서 어떻게 어긋났고 어떻게 고쳤는지**에 관한 기록입니다.

## 🚨 품질분석 봇이 과거 사례 검색을 못 했어요

운영 2주 차에 품질관리팀에서 민원이 들어왔어요 — "불량 원인 조사할 때 과거 비슷한 사례를 같이 찾아달라고 했더니 봇이 자꾸 모른다고만 한다"는 내용이었습니다. 로그를 열어보니 원인이 바로 보였어요.

```
[bot:quality] request to embed-doc REJECTED (virtual key vk-quality-*** not authorized for this model)
```

[EP08](EP08-Hermes-Agent-설치-Bot-Mode-구성.md)에서 가상 키 권한표를 짤 때 품질분석 봇은 `infer-primary`만 허용해뒀었어요 — 설계 당시엔 "불량 원인 후보를 병렬로 조사하는 봇"이라고만 생각해서 임베딩(과거 사례 검색)이 필요할 거라고 예상을 못 했습니다. 실제로 봇을 운영해보고 나서야 빠진 권한이 드러난 셈이에요.

```yaml
# vk-quality 가상 키 권한 수정
allowed_models: [infer-primary, embed-doc]   # embed-doc 추가
```

이 사례 이후로 봇 권한표를 짤 때 "이 봇이 이론적으로 뭘 할지"가 아니라 "실제 업무 요청 로그를 최소 1~2주는 지켜보고 나서 최종 확정하자"는 원칙을 팀 내규로 정했어요.

## 📊 봇별 사용량, 대시보드로 나눠 봤어요

[EP08](EP08-Hermes-Agent-설치-Bot-Mode-구성.md)에서 봇마다 가상 키를 따로 발급해둔 덕분에, LiteLLM의 스펜드 트래킹을 그대로 대시보드에 붙일 수 있었어요.

| 호출 주체 | 일 평균 요청 수 | 일 평균 토큰 | 서브에이전트 평균 스폰 수 |
|---|---|---|---|
| 리서처 봇 | 210건 | 1.2M | 2.8개 (상한 4개) |
| 법무검토 봇 | 95건 | 0.6M | 3.1개 (상한 4개) |
| 품질분석 봇 | 130건 | 0.7M | 2.1개 (상한 4개, embed-doc 추가 후 소폭 증가) |
| Cline·Continue.dev(개발팀) | 340건 | 2.1M | - (Hermes 미경유, 서브에이전트 해당 없음) |

법무검토 봇의 서브에이전트 평균 스폰 수(3.1개)가 상한(4개)에 제일 가깝다는 게 눈에 띄었어요 — 계약서 조항이 많은 문서일수록 다관점 검토(공정거래·개인정보·라이선스)가 거의 매번 상한 근처까지 올라간다는 뜻이었습니다. [EP09](EP09-서브에이전트-동시성-튜닝-GPU-부하-분산-검증.md)에서 잡은 용량 계산이 "이론상 최악"이 아니라 "법무팀은 실제로도 최악에 가깝다"는 걸 이 대시보드로 확인한 셈이에요.

## 🔒 봇마다 시스템 프롬프트에 업무 가드레일을 추가했어요

권한(어떤 모델을 쓸 수 있는가)과는 별개로, 봇이 **어떤 답변 형식을 지켜야 하는가**도 부서마다 달라서 시스템 프롬프트에 명시적으로 박아뒀습니다.

| 봇/도구 | 가드레일 |
|---|---|
| 법무검토 봇 | 근거 조항 번호를 반드시 인용, 확신 없으면 "법무팀 검토 필요"로 명시 |
| 품질분석 봇 | 원인 후보마다 확신도(상/중/하) 표기, 과거 사례 인용 시 사례 번호 명시 |
| 리서처 봇 | 특허·논문 인용 시 출처(문서 ID) 필수, 없으면 "확인 필요"로 표기 |
| Cline·Continue.dev(개발팀) | 1편([EP17](../구축기-v1.0/EP17-Continue.dev-코딩-어시스턴트.md))과 동일 — 코드 변경 이유를 주석 아닌 커밋 메시지로 유도. Hermes 시스템 프롬프트가 아니라 각 도구 자체 설정에 걸어둠 |

이 가드레일 자체는 모델 설정이 아니라 순전히 프롬프트 엔지니어링인데, 비즈니스 봇은 Hermes Bot Mode 단위로, 개발팀은 각 도구(Cline·Continue.dev) 단위로 역할이 딱 분리돼 있어서 "여기엔 이 규칙"이라고 명확하게 관리할 수 있었어요. 만약 하나로 뭉쳐 있었다면 모든 규칙을 프롬프트 하나에 욱여넣어야 했을 텐데, 그 경우 규칙끼리 충돌하거나 씹히는 문제가 훨씬 잦았을 거라고 봐요.

## 📋 이번 편에서 확정한 것

| 항목 | 결정 |
|---|---|
| 권한 재조정 | 품질분석 봇에 `embed-doc` 권한 추가 |
| 권한 설계 원칙 | 이론적 예상이 아니라 최소 1~2주 실사용 로그 확인 후 확정 |
| 사용량 모니터링 | 봇별 가상 키 기준 요청 수·토큰·서브에이전트 스폰 수 대시보드화 |
| 시스템 프롬프트 가드레일 | 봇별로 답변 형식·인용 규칙을 분리 관리 |

다음 편에서는 이 운영 데이터를 바탕으로 전체 모니터링 체계를 잡고, [EP03](EP03-DGX-노드-선정과-독립형-vs-클러스터형-판단.md)·[EP07](EP07-LiteLLM-Router-least-busy-라우팅-구성.md)에서 설계만 해뒀던 노드4 페일오버를 실제 장애 훈련으로 검증합니다.
