# 싱글턴과 멀티턴 (Tool Use)

[[함수 호출 (Tool Use)]] 상황을 난이도로 나누는 가장 기본적인 축입니다. [[Tool-Use 벤치마크 (BFCL)|BFCL]]도 이 둘을 별도 카테고리로 채점합니다.

- **싱글턴** — 요청 한 번에 도구 호출 한 번으로 끝나는 상황. "오늘 서울 날씨 알려줘" → `weather(서울)` 한 번 호출 → 답. 판단할 분기가 거의 없습니다.
- **멀티턴** — 대화가 여러 차례 오가며, 그때그때 **도구를 부를지 말지, 이전 호출 결과를 기억해서 다음 행동을 정할지**를 계속 재판단해야 하는 상황. "버그 찾아줘" → 파일 검색(호출) → 결과 보고 특정 파일 읽기(호출) → 코드 보고 수정(호출) → 사용자가 방향을 바꾸면 그 시점부터 도구를 안 부르고 말로만 답해야 함.

## 왜 멀티턴이 어려운가

핵심 난이도는 "도구를 부르는 것" 자체가 아니라 **"지금은 도구를 부르지 말아야 할 타이밍을 알아채는 것"**입니다. 이미 답이 나왔는데 불필요하게 다시 파일을 읽으러 가거나, 사용자가 계획을 바꿨는데도 이전 계획대로 도구 호출을 계속 이어가는 식의 실수가 대표적입니다. [[Tool-Use 벤치마크 (BFCL)]]에서도 모델 체급과 무관하게 "언제 도구를 안 불러야 하는지" 판단과 "멀티턴 대화에서의 메모리 관리"를 공통 약점으로 꼽습니다.

## 코딩 에이전트는 사실상 항상 멀티턴

[[Cline]] 같은 자율 코딩 에이전트는 본질적으로 "여러 파일을 오가며 계획→실행→재판단을 반복"하는 작업이라, 벤치마크상 싱글턴 점수가 좋아도 실제 체감 성능은 멀티턴 점수가 좌우합니다. [EP20](../../docs/구축기-v1.0/EP20-에이전트-심화-Cline-BFCL.md)에서 Qwen3-235B가 싱글턴은 71~72%대로 양호했지만 멀티턴은 상대적으로 약하다고 실측된 것도 같은 이유이고, 이 종합 성적이 [[Tool-Use 벤치마크 (BFCL)]] 전체 순위에서 밀리는 원인이 됩니다. 대응은 모델을 바꾸는 대신 대화당 도구 호출 횟수 제한과 승인 게이트를 촘촘히 켜는 운영상의 우회였습니다 — 멀티턴 약점 자체를 해결한 건 아니라는 점에 유의해야 합니다.
