# 로그 집계

여러 서버·컨테이너에 각각 흩어져 있는 로그 파일을 하나의 중앙 저장소로 모아, 검색·필터링·[[상관관계 ID]] 기준 상관관계 분석을 한곳에서 할 수 있게 만드는 것입니다. EP13에 "Open WebUI 로그 + nginx 액세스 로그"라고만 나오고 어디로 모으는지가 없는데, 이 상태면 장애가 났을 때 결국 서버 여러 대에 접속해 각각 `grep`을 돌려야 한다는 뜻입니다.

## 메트릭과 무엇이 다른가

[[Prometheus]] 같은 메트릭은 "GPU 사용률이 몇 %다"처럼 이미 숫자로 요약된 시계열이라 저장 비용이 낮고 "무엇이 이상한가"를 빠르게 보여줍니다. 로그는 그 순간 실제로 벌어진 일의 원문(요청 본문, 에러 스택, 응답 상태 코드)이라 정보량은 훨씬 많지만 저장 비용도 비쌉니다. EP13의 장애 복기 순서 — "메트릭으로 이상 감지 → 로그로 원인 특정" — 가 이 둘의 전형적인 역할 분담입니다.

## 폐쇄망에서의 도구 선택

풀텍스트 인덱싱을 하는 ELK(Elasticsearch·Logstash·Kibana)나 OpenSearch는 검색이 강력하지만 인덱싱 자체가 무거워 GPU 서버 옆에 얹기엔 자원 부담이 큽니다. [[Loki]]는 로그 본문이 아니라 라벨(서비스명·레벨 등)만 인덱싱해 훨씬 가볍고, 이미 [[Grafana]]로 대시보드를 쓰고 있다면 같은 벤더 스택이라 메트릭·로그를 한 화면(Explore)에서 같이 보는 이점도 있습니다. 반대로 로그 본문 자체를 정교하게 전문 검색해야 하는 요구(예: 특정 계좌번호 패턴이 로그에 남았는지 감사 조회)가 크다면 ELK/OpenSearch 쪽이 맞을 수 있습니다.

[[Podman]] 환경에서는 컨테이너 로그 드라이버를 journald나 파일로 통일해두고, Loki의 수집 에이전트인 Promtail이 이를 긁어가게 하는 구성이 일반적입니다 — [[RHEL 9]] 위에서 journald는 기본 로깅 경로라 별도 설정 없이도 붙이기 쉽습니다.

## 무엇을 로그로 남길지는 보안과 직결된다

사용자 프롬프트 원문을 로그에 그대로 남기면 [[PII 마스킹]] 이전 단계의 개인정보가 로그 저장소에 고스란히 쌓이는 셈이라, "게이트웨이 진입 전 원문"과 "마스킹 후"의 어느 시점 로그를 남기고 어느 시점은 남기지 않을지를 설계 단계에서 정해야 합니다. 이건 운영용 로그 보존 정책과, 규제가 요구하는 [[감사 로그와 WORM|감사 로그]] 보존 정책이 서로 다른 요구사항을 가진다는 점과도 이어집니다.

## 관련
- [[관측성]] — 로그가 채우는 세 기둥 중 하나
- [[Loki]] · [[Prometheus]] — 폐쇄망에서 짝을 이루는 로그·메트릭 도구
- [[상관관계 ID]] — 트레이싱 없이도 로그를 재조립하는 열쇠
- [[감사 로그와 WORM]] — 같은 "로그"라도 보존 요구가 다른 별도 범주
- [[PII 마스킹]] — 로그에 무엇을 남길지 정할 때 충돌하는 개인정보 이슈
- [[Podman]] · [[RHEL 9]] — 로그 수집 경로가 실제로 걸리는 실행 환경
