# 사전학습 데이터 노출도 판단

"이 모델이 이 도메인 특화 기술(전자정부프레임워크 같은 니치 프레임워크, 사내 전용 라이브러리 등)을 학습했을까?"는 이론으로 단정하기 어렵고, 대신 몇 가지 근거를 조합해 개연성을 가늠하는 게 현실적입니다.

## 노출 가능성을 높이는 조건

- **오픈소스 여부와 기간** — 소스가 공개돼 있고 공개된 지 오래됐을수록 [[사전학습 데이터 파이프라인|사전학습 데이터]]에 포함될 확률이 올라갑니다. GitHub 공개 저장소는 대부분의 코드 특화 모델이 대량으로 스크래핑하는 대표적인 소스입니다.
- **생태계 규모** — 같은 오픈소스라도 전 세계 코드량에서 차지하는 비중이 작은 니치 프레임워크(예: 특정 국가의 공공기관 전용 프레임워크)는, 학습은 됐어도 학습량 자체가 희박해 "얕게만 안다"에 그칠 가능성이 높습니다.
- **기반 기술과의 유사성** — 니치 프레임워크가 훨씬 널리 쓰이는 기반 기술(예: Spring) 위에 얹혀 있다면, 그 프레임워크 자체를 몰라도 기반 기술 지식으로 어느 정도 유추해 답할 수 있습니다. 다만 이건 프레임워크 고유의 클래스명·설정 관례까지 정확히 아는 것과는 다릅니다.

## 노출 가능성을 낮추는 조건

- **폐쇄적 배포 환경** — 실제 활용 코드의 상당수가 조직 내부망·비공개 저장소에만 있고, 공개된 건 공식 템플릿·샘플 정도라면, 모델은 "뼈대"만 봤을 뿐 "현업 커스터마이징 패턴"은 거의 못 봤을 가능성이 큽니다.
- **비영어권 특화 용어** — 학습 데이터의 상당 부분이 영어권 코드에 편중돼 있어, 특정 언어권 고유의 클래스명·API·설정 관례는 상대적으로 노출이 적습니다.

## 이론보다 직접 테스트가 빠르다

노출도를 논쟁으로 가리기보다, 그 도메인의 구체적이고 검증 가능한 질문(특정 클래스명, 패키지 구조, 설정 파일 형식 등)을 직접 던져 답이 검증 가능하게 구체적인지, 아니면 그럴듯하지만 틀린 [[환각]]인지를 확인하는 편이 빠르고 정확합니다.

## 얕다고 판단되면

- **[[RAG]]** — 공식 문서·사내 코드를 검색 컨텍스트로 붙여 모델이 모르는 최신·특화 지식을 보완
- **[[LoRA (파인튜닝)]]** — 소량의 도메인 특화 데이터로 직접 파인튜닝

둘 다 "모델이 원래 몰랐던 지식"을 사후에 주입하는 표준적인 두 경로이며, 어느 쪽을 고를지는 데이터 양·최신성 요구·비용에 따라 갈립니다.

## 실제 사례 — 전자정부프레임워크

전자정부프레임워크의 공식 가이드 저장소(`eGovFramework/egovframe-docs`)를 실제로 확인해보면, 마크다운 문서 678개·전체 약 5.1MB로 실행환경·개발환경·공통컴포넌트 세 영역이 깔끔하게 구조화돼 있습니다. 이 정도 규모는 [[청킹|청킹]]·[[임베딩과 벡터DB|임베딩]] 파이프라인으로 다루기 아주 수월한 크기입니다.

더 결정적인 건 이 저장소 루트에 **`llms.txt`**(llmstxt.org 규격)가 이미 공식적으로 포함돼 있다는 점입니다 — "LLM·AI 에이전트가 이 문서를 정확히 탐색·인용하게 하려고" 프레임워크 측이 직접 만든 인덱스입니다. 즉 이 사례에서는 "노출도가 얕으니 RAG로 보완하라"는 결론에서 한 걸음 더 나아가, **RAG용 인덱스 자체가 이미 공식적으로 준비돼 있는** 유리한 조건이 확인됩니다. LoRA까지 갈 필요 없이 RAG만으로 충분할 가능성이 높다는 뜻입니다.

## 관련
- [[환각]] — 노출되지 않은 지식에 대해 모델이 그럴듯한 오답을 내는 현상, 이 판단이 필요한 이유 자체
- [[RAG]] · [[LoRA (파인튜닝)]] — 노출도가 낮다고 판단됐을 때의 보완 경로
- [[사전학습 데이터 파이프라인]] — 애초에 무엇이 학습 데이터에 들어가는지의 상위 개념
- [[스캐폴드 효과 (에이전트-모델 궁합)]] — "이 모델이 이 작업에 맞는가"를 실측으로 확인해야 한다는 같은 원칙의 다른 적용
- [[청킹]] — 확인된 문서 규모를 실제로 RAG 파이프라인에 넣을 때 거치는 다음 단계
