# 함수 호출 (Tool Use)

모델은 뇌, 도구는 손, 함수 호출(function calling)은 그 둘을 잇는 신경계에 비유할 수 있습니다. 모델 자신은 아무것도 실행하지 않습니다 — "어떤 함수를 어떤 인자로 호출할지"를 구조화된 JSON으로 출력하는 게 전부고, 실제 실행은 애플리케이션 코드가 담당합니다.

## 다섯 단계 루프

1. 사용자가 애플리케이션에 메시지를 보냄
2. 모델이 메시지와 함께 도구 정의(JSON Schema 형식) 목록을 받음
3. 모델이 함수 이름·인자를 담은 구조화된 tool call을 출력
4. 애플리케이션이 그 함수를 실제로 실행하고 결과를 확보
5. 결과가 다시 대화 컨텍스트로 들어가고, 모델이 이를 바탕으로 최종 답을 생성

이 사이클은 한 질의당 여러 번 반복될 수 있습니다 — 검색 결과를 보고 추가로 계산 도구를 부르는 식입니다.

## 도구 정의 스키마

각 도구는 JSON Schema 객체로 선언합니다.

```json
{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "지정한 도시의 현재 날씨를 반환한다",
    "parameters": {
      "type": "object",
      "properties": {
        "city": { "type": "string", "description": "도시 이름" }
      },
      "required": ["city"]
    }
  }
}
```

`description`의 품질이 도구 선택 정확도에 직접 영향을 줍니다 — 모호한 설명은 모델이 엉뚱한 도구를 고르거나 아예 안 부르는 결과로 이어집니다.

이 메커니즘은 [[구조화된 출력]]과 같은 JSON Schema 도구를 쓰지만 목적이 다릅니다. 구조화된 출력은 출력 자체가 최종 산출물이고, 함수 호출은 출력이 "이걸 실행해달라"는 중간 요청입니다.

## Tool Choice — 도구를 쓸지 말지 누가 정하는가

- **Auto(기본)** — 모델이 도구를 쓸지 직접 답할지 스스로 판단
- **Required** — 최소 하나의 도구는 반드시 호출
- **특정 함수 강제** — 라우팅 로직 등에서 특정 도구 하나만 부르도록 고정

## 병렬 함수 호출

GPT-4o·Claude 같은 최신 모델은 한 응답 안에 여러 tool call을 동시에 출력할 수 있습니다. "도쿄와 뉴욕 날씨 알려줘"라는 질문에 순차적으로 두 번 왕복하는 대신 두 개의 날씨 API 호출을 한 번에 내보내는 식이며, 다단계 질의의 지연시간을 60~80% 줄입니다.

## 보안 — 협상 불가능한 다섯 원칙

도구가 실제 시스템(DB·파일시스템·코드 실행 환경)에 닿는 순간 함수 호출은 보안 표면이 됩니다.

1. 모델이 생성한 SQL을 DB에 그대로 넘기지 않는다 — 항상 파라미터화하고 allowlist를 쓴다.
2. "아무 함수나 실행"하는 범용 도구를 만들지 않는다 — 함수를 명시적으로 allowlist한다.
3. 실행 전에 모든 인자를 타입·범위·형식 기준으로 검증한다.
4. 모델에 돌려주기 전에 결과를 정제한다(API 키·PII·내부 오류 메시지 필터링 — [[PII 마스킹]] 참고).
5. 대화당 도구 호출 횟수를 제한한다(10~20회 권장) — 무한 루프를 끊는 안전장치다.

이런 방어는 [[가드레일]]에서 다루는 입력·출력 검증과 같은 층위의 문제입니다 — 함수 호출은 그 검증이 특히 "실행 권한"과 맞물리는 지점입니다.

## 에러 처리 — 예외 대신 구조화된 실패

도구 실행이 실패하면 예외를 던지는 대신 구조화된 메시지를 돌려줍니다.

```json
{ "error": true, "message": "City 'Toky' not found. Did you mean 'Tokyo'?", "code": "CITY_NOT_FOUND" }
```

모델은 이런 힌트가 담긴 실패 메시지에서는 스스로 복구(오타 수정 후 재시도 등)하지만, 그냥 스택 트레이스나 일반 예외 문구만 받으면 복구하지 못하고 같은 실수를 반복하는 경향이 있습니다.

## 표준화된 도구 정의 — MCP로 이어지는 문제

애플리케이션마다 도구 정의를 새로 짜야 한다면, 같은 날씨 API 하나를 Claude Code용·Cursor용·사내 챗봇용으로 세 번 구현해야 합니다. 이 중복을 없애기 위해 도구·리소스를 표준 프로토콜로 공개하고 소비하는 방식이 [[MCP (Model Context Protocol)]]입니다.
