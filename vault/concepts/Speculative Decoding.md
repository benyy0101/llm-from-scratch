# Speculative Decoding

작은 draft 모델이 여러 [[토큰]]을 미리 추측하고, 큰 모델이 그 추측을 한 번에 검증하는 방식입니다. [[Prefill과 Decode|Decode]] 단계가 토큰을 하나씩만 순차적으로 생성해야 하는 병목을 일부 우회하는 최신 기법으로, [[5단계 프로덕션 서빙]] 이후의 심화 주제입니다.

## 구체적으로 왜 빨라지는가

70B 모델이 토큰 하나에 30ms가 걸리고, 3B짜리 draft 모델은 3ms만 걸린다고 하면 — draft 모델이 토큰 5개를 순서대로 추측하는 데 `5×3ms=15ms`, 70B 모델이 그 5개를 한 번의 순전파로 동시에 검증하는 데 30ms, 합쳐서 45ms. 70B 모델 혼자 토큰 5개를 순차 생성했으면 `5×30ms=150ms`였을 일이 45ms로 줄어듭니다. 핵심은 "검증"이 [[Query·Key·Value|어텐션]] 계산의 병렬성을 그대로 활용할 수 있다는 점입니다 — 5개 토큰의 정답 여부를 하나씩 확인하는 게 아니라, [[GPT와 인과적 언어모델링]]에서 다룬 것처럼 시퀀스 하나를 통째로 넣어 한 번의 순전파로 5개 위치의 확률분포를 동시에 뽑아내기 때문입니다.

## 수락/거부 규칙 — 왜 이래도 되는가

draft 토큰을 그냥 다 받아들이면 작은 모델 수준으로 품질이 떨어질 것 같지만, 실제로는 **큰 모델의 확률분포를 정확히 보존하는** 수락/거부 규칙을 씁니다. draft 모델이 토큰에 매긴 확률을 p, 검증 모델이 매긴 확률을 q라 하면, 균등 난수 `u`를 뽑아 `u < min(1, q/p)`일 때만 수락합니다. 거부되면 그 자리에서 `(q-p)`의 양수 부분을 정규화한 "잔차 분포"에서 새로 하나를 뽑아 대체합니다. 이 수학적 장치 덕분에 최종적으로 나오는 토큰 분포는 draft 모델과 무관하게 검증 모델 혼자 생성했을 때와 통계적으로 동일합니다 — draft 모델은 순전히 속도를 위한 "제안자"일 뿐, 품질에는 관여하지 않는다는 뜻입니다.

## 수락률이 성능을 좌우한다

draft 토큰이 얼마나 자주 받아들여지는지(수락률 α)에 따라 이득이 크게 갈립니다. α=0.75, 한 번에 5개를 제안하는 경우 대략 3배 정도 큰 모델 호출 횟수가 줄고, 실측 기준 벽시계 시간은 약 2.5배 개선되는 정도로 보고됩니다.

| 방식 | 특징 | 대략적 속도 향상 |
|---|---|---|
| 기본 draft 모델 | 별도의 작은 모델을 그대로 사용 | 1.8~2.3배 |
| Medusa | 별도 모델 없이 검증 모델 자체에 여러 예측 헤드를 추가 | 2~3배 |
| EAGLE | draft가 검증 모델의 마지막 층 은닉 상태를 재사용해 수락률을 0.85 이상으로 끌어올림 | 3~4배 |
| Lookahead | 별도 모델 없이 자체적으로 추측(self-speculation) | 1.3~1.6배 |

## 실무 제약

거부된 draft 토큰은 애초에 확정된 결과가 아니었으므로, 그 토큰들을 위해 미리 채워뒀던 [[KV 캐시]] 항목도 되돌려야 합니다 — 실제 서빙 엔진(vLLM 등)은 이를 위해 별도의 스크래치 캐시 버퍼로 롤백을 구현합니다. 그리고 생성할 토큰 수가 1~5개로 아주 적은 요청이나, 샘플링 온도가 높아 수락률 자체가 낮아지는 상황에서는 draft 오버헤드가 이득을 넘어서므로 오히려 쓰지 않는 게 낫습니다.
