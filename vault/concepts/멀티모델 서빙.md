# 멀티모델 서빙

[[모델 서빙과 서비스 배포]]에서 짚었듯 실제 [[RAG]] 서비스는 LLM 서빙 하나만으로 끝나지 않습니다 — 임베딩 모델이 최소 하나 더 떠 있어야 하고, 여기에 [[리랭커]]·자동완성용 소형 코드 모델 등을 더하면 한 GPU 노드 안에 **여러 모델이 동시에 상주**하는 게 일반적인 운영 형태입니다.

## 왜 하나로 안 끝나나

- **역할 분담** — 코딩·복잡한 추론엔 큰 모델, 임베딩엔 전용 소형 모델, 빠른 응답이 필요한 곳엔 경량 모델
- **비용/속도 최적화** — 모든 요청에 가장 큰 모델을 쓸 필요는 없음
- **버전 비교/실험** — 신규 모델을 운영 모델과 나란히 띄워 검증

## 올리는 방법 세 가지

1. **GPU를 모델별로 정적 분할** — 노드 안의 GPU를 용도별로 나눠 각각에 [[vLLM]] 인스턴스를 띄움. [[VRAM]] 여유분만큼 자유롭게 조합 가능.
2. **서빙 엔진 자체의 멀티모델 지원** — [[Ollama]]는 여러 모델을 받아두고 필요할 때 로드/언로드하며, [[NVIDIA NIM]]·Triton Inference Server는 애초에 멀티모델 서빙을 위해 설계됨.
3. **[[LiteLLM]] 게이트웨이로 앞단 통합** — 여러 백엔드(vLLM 인스턴스 여러 개)를 하나의 API 창구로 묶고, 요청 종류에 따라 적절한 모델로 라우팅.

```
클라이언트 요청
  → LiteLLM 게이트웨이
      ├─ "코딩" 요청 → 메인 모델 (GPU 0-3)
      ├─ "임베딩" 요청 → BGE-M3 (GPU 4-5)
      └─ "빠른 응답" 요청 → 경량 모델 (GPU 6-7)
```

## 흔한 오해 — "메인 모델도 여러 개 띄운다"

멀티모델 서빙이라고 해서 서로 다른 거대 LLM 여러 개를 동시에 운영하는 경우는 드뭅니다. [EP14. 모델 업데이트 전략](../../docs/구축기/EP14-모델-업데이트-전략.md)에서 다룬 모델 교체·검증 부담이 커지기 때문입니다. 실무에서 훨씬 흔한 조합은 **같은 메인 모델의 여러 인스턴스(부하분산·이중화)** + **역할이 다른 소형 모델들(임베딩·리랭커·자동완성)**입니다.
