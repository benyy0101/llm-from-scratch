# 리랭커

[[임베딩과 벡터DB|벡터 검색]]으로 일단 후보를 넉넉히(예: 50개) 빠르게 추린 다음, 그 후보만 질문과 다시 정밀하게 대조해 "진짜 관련 있는 순서"로 재정렬하는 2단계 필터입니다. [[하이브리드 검색]]의 세부 구성요소 중 하나지만, RAG 정확도에 미치는 영향이 커서 별도로 다룰 만합니다.

## 왜 벡터 검색만으로는 부족한가

벡터 검색(그리고 [[하이브리드 검색]]의 BM25도 마찬가지)은 질문과 문서를 **각각 독립적으로** 임베딩한 뒤 그 벡터끼리 거리를 재는 [[임베딩과 벡터DB|bi-encoder]] 방식입니다. 빠르지만, 질문과 문서 사이의 세밀한 상호작용(같은 단어라도 문맥에 따라 관련도가 달라지는 것 등)까지는 담아내지 못해 "의미는 비슷한데 실제 답은 아닌" 문단이 상위권에 낄 수 있습니다.

리랭커는 **cross-encoder** 방식입니다 — 질문과 문서를 하나로 합쳐 모델에 통째로 넣고 관련도 점수를 직접 계산합니다. 그만큼 정확하지만 100~1,000배 느려서, 코퍼스 전체에 이 방식을 쓰는 건 비현실적입니다.

## 그래서 2단계로 나눈다

```
질문 → 벡터 검색(bi-encoder)으로 top-50~100 후보를 빠르게 추림
     → 리랭커(cross-encoder)가 그 후보만 정밀 재채점
     → 상위 5~10개만 LLM 프롬프트에 전달
```

속도(1단계)와 정확도(2단계)를 각자 잘하는 역할에만 쓰는 구조입니다. 도서관에 비유하면, 1단계는 "관련 있어 보이는 책 50권을 서가에서 빠르게 뽑아오는 일", 2단계는 "그 50권을 한 권씩 펼쳐 보고 질문에 진짜 맞는 순서로 다시 줄 세우는 일"입니다.

## 대표 구현체

- **bge-reranker** — [[BGE-M3]]와 같은 BAAI 계열, 오픈소스라 [[폐쇄망]] 반입에 적합
- Cohere Rerank, Voyage Rerank — 상용 API 전용이라 폐쇄망에는 부적합

## 언제 넣을 가치가 있나

문서량이 적거나 정확도 요구가 낮으면 벡터 검색(또는 하이브리드 검색)만으로 충분합니다. 반대로 사내 규정·상품 매뉴얼처럼 **정확한 근거 문단을 짚어야 [[환각]]이 줄어드는 문서QA**에서는 리랭커 한 단을 추가하는 게 체감 효과가 큽니다.
