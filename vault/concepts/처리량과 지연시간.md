# 처리량과 지연시간

배치를 키우면 GPU당 처리량(throughput)은 오르지만, 개별 요청 입장에서는 다른 요청과 같이 대기하는 시간이 늘어 지연시간(latency)이 나빠집니다. 서빙 설정에서 최대 배치 크기·최대 대기 시간을 튜닝하는 게 결국 이 트레이드오프를 조절하는 일입니다 (vLLM의 `--max-num-seqs`가 대표적인 손잡이). 챗봇처럼 응답 체감이 중요하면 지연시간 쪽으로, 배치 문서 요약처럼 응답 속도가 안 중요하면 처리량 쪽으로 기울입니다.

## 왜 배치를 키우면 처리량이 오르는가

[[Prefill과 Decode|Decode]]는 메모리 대역폭 병목입니다 — 토큰 하나를 생성할 때마다 모델 [[가중치]] 전체를 메모리에서 읽어와야 하는데, 그 가중치로 하는 실제 계산량은 GPU 연산력에 비하면 작아서 연산 유닛 대부분이 놀고 있습니다. 그런데 가중치는 모든 요청이 공유합니다 — 한 번 읽어온 가중치로 요청 1개의 토큰만 계산하지 않고 [[배치]]를 키워 요청 64개의 토큰을 동시에 계산하면, 읽기 시간은 거의 그대로인데 그 시간에 처리하는 일의 양이 64배로 늘어납니다.

```mermaid
flowchart TD
    subgraph B1["배치 크기 1"]
        W1["가중치 읽기\n(메모리 대역폭 병목, 고정 시간 T)"] --> C1["계산: 요청 1개의 토큰 1개\n→ T 동안 토큰 1개 생성"]
    end
    subgraph BN["배치 크기 64"]
        W2["가중치 읽기\n(거의 같은 고정 시간 T)"] --> C2["계산: 요청 64개의 토큰 64개\n(GPU 연산 유닛을 병렬로 활용)\n→ T 동안 토큰 64개 생성"]
    end
```

트럭이 창고까지 왕복하는 데 30분 걸린다고 하면, 상자 1개만 싣고 오나 64개를 싣고 오나 왕복 시간은 거의 똑같습니다 — 그러면 64개씩 실어 나르는 쪽이 시간당 배달량이 훨씬 높습니다. Decode에서 "가중치 읽기"가 이 왕복, "토큰 계산"이 상자에 해당합니다. 다만 배치가 계속 커지면 결국 GPU의 실제 연산력(FLOPs)을 다 써버리는 지점이 오고, 거기서부터는 더 키워도 처리량이 오르지 않습니다 — 메모리 병목이 연산 병목으로 넘어가는 지점입니다. 동시에 요청마다의 [[KV 캐시]]도 다 메모리에 올라와 있어야 하므로 VRAM이 배치 크기의 또 다른 상한선이 됩니다.

## 서빙 최적화의 핵심 목표: GPU 연산을 놀리지 않는 것

지금까지 다룬 서빙 기법들을 하나의 렌즈로 다시 보면, 전부 같은 목표로 수렴합니다 — **[[Prefill과 Decode|Decode]]에서 노는 GPU 연산 유닛을 최대한 놀리지 않는 것.** 이건 폐쇄망이라서 특별한 문제가 아니라, 클라우드든 온프레미스든 LLM 서빙 자체의 본질적인 문제입니다.

- **[[배치]]** — 가중치 읽기 한 번에 더 많은 연산을 욱여넣어서, 노는 시간 대비 일하는 양의 비율을 올립니다.
- **[[PagedAttention]]** — 메모리를 낭비 없이 관리해서 더 큰 배치를 담을 여지를 만듭니다.
- **[[Continuous Batching]]** — 요청 하나가 끝나자마자 빈자리를 바로 채워, 노는 시간을 물리적으로 없앱니다.
- **[[양자화]]** — 애초에 옮겨야 할 데이터량 자체를 줄여서, 대기 시간의 비중 자체를 낮춥니다.

[[vLLM]]이 [[Ollama]]보다 프로덕션에 강한 이유도 결국 "이 목표를 얼마나 정교하게 구현했는가"의 차이입니다 — 엔진 이름·브랜드가 본질이 아니라, 이 목표 달성도가 본질입니다.

**예외도 있습니다.** [[Pipeline Parallelism]]의 "파이프라인 버블"은 정반대로, 병렬화 자체가 GPU를 순서대로 기다리게 만들어 오히려 노는 시간을 만들어냅니다 — 이 목표를 일부 희생하는 대신 애초에 한 GPU에 안 들어가던 큰 모델을 돌아갈 수 있게 해주는 트레이드오프입니다. 모든 기법이 "연산을 놀리지 않는다"는 목표 하나로만 수렴하지는 않는다는 것도 함께 기억해두면 좋습니다.

## 정확히 언제 메모리 병목이고 언제 연산 병목인가 — Ops:Byte

"메모리 대역폭 병목"이라는 말을 좀 더 정량적으로 재는 잣대가 **Ops:Byte**(연산 밀도, arithmetic intensity)입니다. GPU 하나가 가진 연산 능력(FLOPS)과 메모리 대역폭(Byte/s)의 비율이 그 GPU의 "전환점"입니다 — A100은 연산 312TFLOPS, 대역폭 2TB/s라 `312e12/2e12 ≈ 156`, 즉 데이터 1바이트당 156번 이상 연산할 일이 있어야 연산 병목으로 넘어갑니다.

실제 작업이 이 기준을 넘는지는 "이번에 읽어온 가중치로 얼마나 많은 연산을 하는가"로 정해집니다.

| 상황 | 대략적인 Ops:Byte | 병목 | 대응 |
|---|---|---|---|
| Decode, 배치=1 | ~1 | 메모리 | [[양자화]]로 읽을 데이터량 자체를 줄임 |
| Decode, 배치=32 | ~32 | 여전히 메모리에 가까움 | [[배치]]를 더 키움 |
| Prefill(긴 프롬프트) | ~4,096 | 연산 | 커널 퓨전 등 연산 자체를 빠르게 |

Decode는 토큰 하나당 가중치 전체를 한 번 읽어서 딱 그만큼만 계산하니 Ops:Byte가 156 근처에도 못 미쳐 메모리 병목에 갇혀 있고, 배치를 키우는 게 바로 이 값을 156에 가깝게 밀어 올리는 행위입니다. 반대로 [[Prefill과 Decode|Prefill]]은 같은 가중치로 프롬프트 토큰 수백~수천 개를 한꺼번에 계산하니 Ops:Byte가 이미 수천 단위로 높아 연산 병목 쪽에 있습니다 — 그래서 Prefill 최적화는 배치를 늘리는 것보다 커널 자체의 연산 효율(FlashAttention 등)을 높이는 방향으로 갑니다.
