# 메모리 대역폭

[[GPU]]가 초당 [[VRAM]]에서 얼마나 많은 데이터를 읽고 쓸 수 있는지를 나타내는 값(예: H100은 초당 3TB)입니다. 연산 능력(FLOPS, "1초에 계산을 몇 번 할 수 있나")과는 완전히 다른 축의 스펙이라서, GPU가 아무리 빨리 계산할 수 있어도 계산할 데이터를 제때 읽어오지 못하면 그 계산력은 그냥 놀게 됩니다.

비유하면, 연산 능력은 "요리사가 손을 얼마나 빨리 놀리는가"이고 메모리 대역폭은 "재료 창고에서 조리대까지 얼마나 빨리 재료를 나를 수 있는가"입니다. 손이 아무리 빨라도 재료가 안 오면 요리사는 기다릴 수밖에 없습니다.

## Prefill은 연산 병목, Decode는 대역폭 병목

[[Prefill과 Decode]]가 정확히 이 두 축으로 갈립니다.

- **Prefill** — 프롬프트 토큰 여러 개를 한 번에 병렬로 계산합니다. 읽어온 [[가중치]] 하나로 토큰 여러 개 몫의 계산을 한꺼번에 처리하니, 데이터를 나르는 시간보다 실제 계산하는 시간이 더 걸립니다 → **연산(compute-bound)** 병목.
- **Decode** — 한 스텝에 토큰을 딱 1개만 생성합니다. 그런데 그 1개를 계산하려고 모델 가중치 전체와 [[KV 캐시]]를 매번 VRAM에서 다시 읽어와야 하는데, 정작 그 데이터로 하는 계산량은 아주 작습니다 → 창고 나르는 시간이 요리 시간보다 압도적으로 길어지는 상황, 즉 **메모리 대역폭(memory-bound)** 병목.

이 병목을 숫자로 재는 잣대가 **Ops:Byte**(연산 밀도)입니다 — GPU의 연산 능력(FLOPS)을 메모리 대역폭(Byte/s)으로 나눈 값이 그 GPU의 "전환점"입니다. A100은 `312TFLOPS / 2TB/s ≈ 156`이라, 읽어온 데이터 1바이트당 156번 이상 연산할 일이 있어야 비로소 연산 병목으로 넘어갑니다. Decode는 이 문턱을 한참 못 넘기 때문에 항상 대역폭 병목 쪽에 남습니다.

## 이 병목이 다른 개념들에 미치는 영향

- **[[양자화]]**: 가중치 자체를 작게 만들면 Decode 때마다 읽어와야 할 바이트 수가 줄어드니 그만큼 빨라집니다 — 양자화가 서빙 속도를 개선하는 이유가 바로 이 대역폭 병목을 줄이는 것입니다.
- **[[처리량과 지연시간|배치(Batching)]]**: 가중치를 한 번 읽어오는 데 걸리는 시간(고정)에 맞춰, 그 한 번으로 요청 1개가 아니라 여러 개의 토큰을 동시에 계산하면 "읽기 시간은 그대로인데 처리량만 늘어나는" 효과를 얻습니다. 즉 배칭은 대역폭 병목을 우회하는 전략입니다.
- **[[KV 캐시]] / FlashAttention**: GPU 내부에는 VRAM(HBM)보다 훨씬 빠른 온칩 메모리(SRAM)가 있습니다(H100 기준 HBM 3TB/s vs SRAM 30TB/s). FlashAttention은 중간 계산 결과를 굳이 느린 HBM에 왕복시키지 않고 빠른 SRAM 안에서 끝내, 같은 대역폭 병목 문제를 다른 각도(계산 경로 자체의 메모리 이동량 축소)로 줄입니다.
- **[[GPU 선택]]**: 애플 실리콘(맥)이 VRAM 용량은 넉넉해도 프로덕션 서빙에서 잘 안 쓰이는 핵심 이유가 메모리 대역폭이 낮기 때문입니다 — 용량이 있어도 그 속도로는 Decode 병목을 감당하기 어렵습니다.
- **[[DGX 멀티노드 아키텍처]]**: 노드 내부 GPU 간 연결(NVLink)과 노드 간 연결(InfiniBand/이더넷)은 대역폭 자릿수가 다릅니다. 여러 노드에 걸친 [[Tensor Parallelism]]이 비효율적인 이유도 결국 노드 간 대역폭이 노드 내부보다 훨씬 낮다는 같은 문제입니다.
