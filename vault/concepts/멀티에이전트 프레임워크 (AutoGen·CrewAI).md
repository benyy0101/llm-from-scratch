# 멀티에이전트 프레임워크 (AutoGen·CrewAI)

[[에이전트 상태 관리 (LangGraph)|LangGraph]]가 State·Node·Edge로 실행 흐름을 명시적인 그래프로 그린다면, AutoGen과 CrewAI는 같은 [[멀티턴과 멀티에이전트 (구분)|멀티에이전트]] 문제를 각각 "대화"와 "역할극"이라는 더 높은 수준의 추상화로 풉니다.

## AutoGen (Microsoft Research) — 대화 중심

에이전트를 `ConversableAgent` 객체로 정의하고, 여러 에이전트가 서로 채팅 메시지를 주고받으며 작업을 진행합니다. `GroupChatManager`가 "다음 발언 차례는 누구인가"를 매 턴 정하는 라우터 역할을 합니다. 사람이 직접 개입하거나 코드를 실행하는 `UserProxyAgent`도 대화 참여자 중 하나로 취급됩니다.

- **장점** — 정확한 실행 순서를 미리 다 못 정해도, 에이전트들이 대화하면서 알아서 다음 담당자를 정하는 유연함
- **단점** — 조율 로직이 그래프처럼 코드에 타입으로 박혀 있는 게 아니라 프롬프트·대화 패턴에 암묵적으로 녹아 있어서, [[에이전트 상태 관리 (LangGraph)|LangGraph]]만큼 "누가 어떤 도구에 접근하는지"를 정적으로 감사하기가 어려움

## CrewAI — 역할 중심

LangChain 생태계와 독립적으로 만들어진 자체 런타임입니다. `Agent`(role·goal·backstory로 정의된 역할), `Task`(에이전트에게 할당된 작업), `Crew`(그 전체를 묶는 팀)로 구성하고, `Process`를 `sequential`(순차) 또는 `hierarchical`(감독자가 위임)로 지정합니다.

- **장점** — "기획자·리서처·작성자"처럼 사람이 조직을 설명하는 방식 그대로 코드가 되기 때문에, 비개발 업무 자동화(리서치 파이프라인, 콘텐츠 제작 등)에 빠르게 적용하기 좋음
- **단점** — 역할·태스크 추상화가 실제 실행 그래프를 가리는 편이라, LangGraph의 조건부 엣지처럼 "이 경우엔 이 노드로"를 세밀하게 통제하기는 상대적으로 어려움

## LangGraph와 언제 갈리는가

[[에이전트 상태 관리 (LangGraph)|LangGraph 노트]]는 "다루려는 작업의 노드를 미리 하나하나 나열할 수 없다면, 애초에 그래프 기반 에이전트로 풀 문제가 아니라는 신호"라고 정리합니다. AutoGen·CrewAI는 정확히 그 반대 상황 — **작업 순서가 실행 전에 완전히 확정되지 않고, 에이전트들이 대화·협상하며 그때그때 정해야 하는 경우** — 를 위한 선택지입니다. 반대로 "허용 도구 집합을 코드에서 처음부터 완전히 열거해야 한다"는 컴플라이언스 요구가 있다면 [[에이전트 프레임워크 선택 기준|LangGraph 쪽이 더 강한 보장을 줍니다]].

## 폐쇄망 반입

[[에이전트 상태 관리 (LangGraph)|LangGraph와 마찬가지로]] 완성품 제품이 아니라 `pip install pyautogen`/`pip install crewai`로 까는 파이썬 라이브러리입니다. 반입 절차도 동일한 패턴을 따릅니다 — 오프라인 pip 미러로 `.whl` 반입, 직접 작성한 에이전트·도구 코드를 컨테이너 이미지로 빌드, 정적 분석 수준의 코드 리뷰.

## 관련
- [[에이전트 상태 관리 (LangGraph)]] — 같은 문제를 명시적 그래프로 푸는 대안, 조율 로직의 감사 가능성 차이
- [[멀티턴과 멀티에이전트 (구분)]] — 이 프레임워크들이 다루는 "몇 명이 일하는가" 축
- [[Hermes Agent]] — 라이브러리를 직접 조립하는 대신 완성품의 Bot Mode로 멀티에이전트를 얻는 대안
- [[에이전트 프레임워크 선택 기준]] — LangGraph·AutoGen·CrewAI·Hermes 중 무엇을 고를지의 종합 판단
