# 하이브리드 검색

[[임베딩과 벡터DB|벡터 검색(dense)]]만으로는 "의미가 비슷한 것"은 잘 찾아도, 정확한 용어·조항 번호처럼 "그 단어가 정확히 들어갔는가"가 중요한 질문에는 약합니다. [[RAG]]에서는 보통 **dense 의미 검색 + sparse 어휘 검색(BM25 계열)**을 함께 사용해 한쪽에서 놓치는 근거를 서로 보완합니다.

## 검색 단서의 차이

| 방식 | 주로 보는 단서 | 예시 |
|---|---|---|
| Dense | 학습된 표현의 유사도 | ‘물에 빠뜨림’과 ‘침수’ 연결 |
| BM25 | 단어 일치·빈도·희소성·문서 길이 | 제품 코드·조항 번호 찾기 |
| 학습된 sparse | 모델이 만든 어휘별 가중치 | 학습된 중요 어휘로 검색 |

**Sparse와 BM25는 동의어가 아닙니다.** Sparse는 표현 방식이고 BM25는 점수 함수입니다. [[BGE-M3]]의 sparse 출력도 BM25와 동일하지 않습니다.

## 후보 병합 — RRF

Dense 30개와 BM25 30개가 20개 겹치면 합집합은 40개입니다. 서로 다른 점수를 그냥 더하면 척도가 다른 문제가 생기므로, 동일 청크를 합친 뒤 **[[RRF]]**처럼 "각 목록에서 몇 등이었는지"를 기준으로 순서를 다시 매기는 방식을 씁니다 — 두 목록 모두에서 상위권이었던 항목이 최종 결과에서도 위로 올라옵니다. [[Qdrant]]는 dense·sparse 벡터를 한 컬렉션에서 같이 관리하고 이 융합까지 지원합니다.

합집합에는 각 검색의 결과가 포함되지만, 병합 후 상위 N개로 자르면 정답이 다시 빠질 수 있습니다. **최종 후보 수를 맞춘 Recall@N**으로 비교해야 합니다.

## 리랭킹 — 빠른 후보에서 정확한 순위로

하이브리드 검색까지 거쳐도 top-k 결과의 "순서"가 최적이라는 보장은 없습니다. 지금까지 다룬 벡터 검색·BM25는 모두 질문과 문서를 독립적으로 처리하는 [[임베딩과 벡터DB|bi-encoder]] 방식이라 후보를 빠르게 좁히는 데는 강하지만, 질문과 문서 사이의 세밀한 상호작용까지는 담아내지 못합니다. 실무 표준은 2단계 파이프라인입니다 — 하이브리드 검색(bi-encoder + BM25 + RRF)으로 top-50~100 후보를 빠르게 추리고, 전용 cross-encoder로 그 후보만 다시 채점해 최종 top-5~10을 뽑아 프롬프트에 넣습니다. 자세한 내용은 [[리랭킹]]과 [[리랭커]]를 참고하세요.

## 쿼리 변환 — Query Rewriting과 HyDE

사용자가 실제로 입력하는 질문이 검색에 적합하지 않은 경우가 많습니다. **Query Rewriting**은 "그 새 정책 그거 뭐였지" 같은 모호한 질문을 "최근 정책 변경 사항"처럼 검색하기 좋은 형태로 LLM이 다시 씁니다. **HyDE(Hypothetical Document Embeddings)**는 한 단계 더 나아가 — 질문에 대한 그럴듯한 가상의 답변을 LLM으로 먼저 생성한 뒤, 원래 질문 대신 이 가상 답변을 임베딩해서 검색합니다. 질문(의문문)과 실제 문서(서술문)는 같은 내용이라도 표현 형태가 달라 임베딩 공간에서 멀어지는 경우가 있는데, 가상의 "답변 형태" 텍스트로 검색하면 실제 문서와 더 가까워집니다. 추가 LLM 호출 한 번만큼 지연시간(500~2,000ms)이 늘지만, 원 질문 자체가 부실할 때 검색 품질을 끌어올립니다.

## Parent-Child 청킹과 메타데이터 필터링

[[청킹]]에는 근본적인 딜레마가 있습니다 — 청크를 작게 자르면 검색은 정밀해지지만 LLM에 넘길 문맥이 부족해지고, 크게 자르면 문맥은 충분해도 검색 정밀도가 떨어집니다. Parent-Child 청킹은 이 둘을 분리해서 해결합니다 — 검색은 작은 자식 청크(예: 128토큰) 단위로 정밀하게 하되, 실제로 프롬프트에 넣을 때는 그 자식이 속한 더 큰 부모 청크(예: 512토큰)를 대신 반환합니다. 날짜·출처·카테고리 같은 메타데이터로 벡터 검색 전에 코퍼스를 먼저 좁혀두는 메타데이터 필터링도, 대규모 문서 집합에서 무관한 결과를 줄이는 흔한 보완책입니다.
