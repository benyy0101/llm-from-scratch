# 상관관계 ID

요청 하나가 [[표준 아키텍처|여러 계층]]을 거쳐 처리될 때, 그 요청을 처음 받은 지점(보통 nginx나 게이트웨이 진입부)에서 고유 ID를 하나 발급해 이후 모든 계층에 헤더로 그대로 전달하는 값입니다. 각 계층은 자신의 로그나 메트릭에 이 ID를 같이 남기고, 나중에 이 ID 하나로 여러 서버·컨테이너에 흩어진 기록을 "이 요청 하나의 이야기"로 재조립할 수 있습니다.

이 아이디어를 표준화한 게 W3C Trace Context 규격의 `traceparent` 헤더입니다. [[분산 트레이싱]]은 이 ID에 시작·끝 시각과 계층 정보를 더 붙여 자동으로 시각화한 것이고, 상관관계 ID 자체는 그보다 훨씬 단순합니다 — 트레이싱 백엔드 없이 [[로그 집계]] 도구에서 이 ID로 필터만 걸어도 "이 요청이 어느 서버에서 무슨 로그를 남겼는지"는 수동으로 짜 맞출 수 있습니다. 트레이싱이 부담스러운 초기 단계에서는 이 ID 전파만 먼저 해두는 게 비용 대비 효과가 큽니다.

## 사슬이 끊기는 지점을 조심해야 한다

이 방식의 약점은 계층 하나라도 이 ID를 받아서 다시 넘기지 않거나 로그에 남기지 않으면, 그 지점에서 추적의 사슬이 끊긴다는 겁니다. 예를 들어 [[nginx]] 액세스 로그 포맷에 기본적으로는 이 ID가 안 찍히므로 `log_format`에 헤더 값을 명시적으로 추가해야 하고, [[Open WebUI]]가 이 ID를 받아 [[LiteLLM]] 호출 헤더에 그대로 실어 보내는지도 확인이 필요합니다. [[LiteLLM]]은 자체적으로 요청마다 `request_id`를 발급·로깅하지만, 이게 앞단(nginx·Open WebUI)에서 넘어온 ID와 같은 값인지 아니면 LiteLLM이 새로 발급한 별개의 값인지에 따라 추적 가능 범위가 달라집니다 — 앞단 ID를 그대로 물려받게 설정해야 처음부터 끝까지 하나의 ID로 추적됩니다.

## 관련
- [[분산 트레이싱]] — 이 ID에 시간·계층 정보를 더해 자동 시각화한 상위 개념
- [[로그 집계]] — 이 ID만으로 여러 서버 로그를 재조립하는 실전 활용법
- [[LiteLLM]] · [[nginx]] — 이 ID를 실제로 발급·전파·기록해야 하는 계층
- [[관측성]] — 세 기둥을 엮는 접착제 역할
